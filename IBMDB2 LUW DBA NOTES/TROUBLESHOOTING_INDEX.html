A-01 Host, server, virtualization, capacity, and failure domains

  • Db2 latency rises while guest CPU appears idle. — vCPU descheduling or contention on an oversubscribed host.; evidence: mpstat steal, hypervisor CPU ready, and Db2 per-EDU deltas.. Safe response
  • Failover host is nominally large but runs out of headroom. — Capacity counted from installed size instead of usable post-failure capacity.; evidence: Peak CPU/memory demand plus all-active and failover topology.. Safe response

A-02 Linux identity, filesystems, permissions, limits, and services

  • A Db2 path returns permission denied despite write permission on the leaf. — A parent directory lacks execute/traverse permission or an ACL mask removes rights.; evidence: id, namei -l, getfacl, mount flags, and process UID.. Safe response
  • Service starts manually but not after reboot. — Service manager does not load the interactive instance profile or starts before a required mount.; evidence: systemd unit, journal, environment/profile, dependency ordering, and account lookup.. Safe response

A-03 CPU, memory, process, paging, and Db2 EDU diagnosis

  • Load average is high but CPU idle and iowait is elevated. — Tasks are blocked on I/O or locks, not runnable CPU demand.; evidence: vmstat blocked queue, iostat latency, db2pd -wlocks, and -applications.. Safe response
  • Db2 process is killed or host swaps during a busy period. — Host/cgroup limit or concurrent memory consumers exceed headroom.; evidence: kernel journal OOM records, cgroup memory.events, Db2 memory sets, and process RSS.. Safe response

A-04 Storage, filesystems, multipath, capacity, and I/O diagnosis

  • Archive creation fails although df -h reports free space. — Inode exhaustion or unusable mount/permission, rather than block capacity.; evidence: df -i, archive destination permissions, mount events, and db2diag archive message.. Safe response
  • Filesystem remains full after a large file is removed. — A process still holds a deleted file open.; evidence: lsof +L1, process FD list, and filesystem usage.. Safe response

A-05 Networking, DNS, ports, firewalls, time, and client/server evidence

  • TCP connection is refused immediately. — No listener on the port or service not started/bound.; evidence: server ss -ltnp, service mapping, Db2 instance status and db2diag startup record.. Safe response
  • TLS client rejects a valid server certificate. — Trust store/name mismatch or clock skew.; evidence: client trust chain, certificate SAN/expiry, system time, client driver and TLS trace.. Safe response

  • Encrypted image cannot be opened because key material is unavailable — key escrow/credential or provider configuration is missing; evidence: image header, encryption options, key-manager audit, key label/version, and restore diagnostics. Safe response
  • Wrong image or alias selected — ambiguous filename or cross-member image selection; evidence: image header, database/member identity, timestamp, history, and target alias. Safe response

K-03 Availability/change practicum: HADR, upgrade, failover, and rollback decisions

  • Standby disconnected or replay lagging — transport failure or replay bottleneck; evidence: HADR state, send/receive/replay position, db2diag, network and archive. Safe response
  • Former primary may still accept writes — dual-writer risk or stale route; evidence: old host state, fencing, route, storage lease and cluster control. Safe response
  • HADR transition or upgrade gate is blocked — upgrade in progress, unsupported sequence, or standby outside takeover-eligible state; evidence: HADR role/state, utility/upgrade status, log positions, db2diag, and fix-pack matrix. Safe response

K-04 Enterprise capstone: architecture, security, recovery, performance, and operations

  • Takeover succeeded but clients fail — database role changed but route/trust dependency did not; evidence: role, fencing, DNS/load balancer, TLS trust, credentials, firewall, retries. Safe response
  • Bad data propagated to standby — HA confused with independent corruption recovery; evidence: replication mode/lag, transaction timeline, backup and PIT test. Safe response

I-01 Production change design, blast radius, stop criteria, rollback, and acceptance

  • Accepted change but no service effect — wrong scope or deferred activation; evidence: target scope, effective value, activation, member, and app telemetry. Safe response
  • Rollback restores value but not service — consequences were not fully reversible; evidence: timeline, utilities, retries, route changes, and data effects. Safe response

I-06 Capacity planning and reference architectures with recovery/failover headroom

  • Normal load fits, failover saturates — capacity modeled only for normal state; evidence: per-node demand, skew, replay, client routing, and app metrics. Safe response
  • Space exists but restore misses RTO — volume capacity mistaken for recovery throughput; evidence: image size, media/network throughput, logs, and restore time. Safe response
