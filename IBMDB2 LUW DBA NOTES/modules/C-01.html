SQL and Transaction Fundamentals for DBAs

Use controlled SQL to inspect and change data while understanding transaction boundaries, isolation, and error recovery.

Level: Intermediate · Effort: 2 hours
Prerequisites: A-04 and B-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish DDL, DML, and transaction control.
  • Explain commit, rollback, autocommit, and isolation.
  • Use predicates and row counts to bound a change.

How it works and when to use it

A successful SQL statement reports that Db2 executed the statement; it does not prove that the intended business rows changed. A unit of work begins with transactional SQL and ends at COMMIT or ROLLBACK. Client autocommit can make each statement permanent immediately, so confirm client behavior before a multi-step repair. Isolation determines which concurrent changes can be observed and which locks may be held.

Decision rule: Preview the target row set and expected count, run the change in a controlled transaction, compare affected rows to the expectation, and commit only when the invariant holds.

Worked examples and commands

SELECT row count before a change

db2 "SELECT COUNT(*) FROM APP.ORDERS WHERE STATUS = 'PENDING'"

Expected / interpretation: The count is a baseline, not a lock on the qualifying rows. Recheck or use an application-safe transaction when concurrent writes matter.

Bounded update inside a unit of work

db2 "UPDATE APP.ORDERS SET STATUS = 'READY' WHERE ORDER_ID = 10042"

Expected / interpretation: Inspect the CLP affected-row message; The CLP reports affected rows; compare that count to the expectation. Commit only after validating the exact row.

Explicit rollback when a guard fails

db2 "ROLLBACK"

Expected / interpretation: Ends the current unit of work. It cannot undo work already committed by autocommit.

Transaction flow: Inspect, change, validate, then commit or roll back

The commit decision follows the verified postcondition; client autocommit can remove the rollback branch.

Known issues, errors, fixes, and verification

The change affects zero or too many rows.

Likely cause: Predicate, current schema, case/quoting, data assumptions, or concurrent state is wrong.

Fix: Stop before commit; verify object identity and predicate with a SELECT, then use a key-based predicate and expected row-count guard.

Verify: Read back by primary key in a new transaction and reconcile counts.

SQL0911N reports a deadlock or lock timeout.

Likely cause: Concurrent transactions conflict or hold locks too long.

Fix: Read the reason code and diagnostic evidence, roll back the whole unit of work, reduce lock duration, and retry only if the operation is idempotent.

Verify: Confirm rollback completed and inspect the competing transaction before controlled retry.

A user expects ROLLBACK to reverse prior statements, but rows remain changed.

Likely cause: The client committed automatically or the statements were separated by commit boundaries.

Fix: Disable autocommit in the client before the work and begin the transaction before issuing mutations.

Verify: In a disposable table, prove rollback from a second connection before using the workflow.

Hands-on lab: Guard a small data correction

Objective: Demonstrate preview, transaction, row-count validation, and rollback.

  1. Create a disposable APP lab table with a unique key and synthetic rows.
  2. Select the exact key and record the expected value.
  3. Update one key, inspect the result, then rollback.
  4. Repeat and commit only after matching the expected postcondition.

Answer key: The corrected row is selected by a unique key; the observed affected-row count is one; a second connection confirms committed state only after explicit commit.

Cleanup: Drop only the disposable lab table after confirming the lab schema.

Review question and answer

Question: Why is a successful UPDATE not sufficient evidence that a correction is right?

Answer: The command can update zero or unintended rows. Validate target keys, affected-row count, and the postcondition inside the intended transaction.
