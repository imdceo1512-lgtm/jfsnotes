SQL Compilation, Access Plans, EXPLAIN, and db2exfmt

Capture and read the optimizer access plan to locate scans, joins, sorts, estimates, and costly operators.

Level: Advanced · Effort: 2 hours
Prerequisites: C-02, C-03, and H-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Prepare explain tables and capture a plan.
  • Interpret operator sequence, estimated rows, and costs.
  • Compare plan evidence to actual workload metrics.

How it works and when to use it

Db2 compiles SQL into an access plan using schema, constraints, statistics, parameterization, configuration, and optimization settings. EXPLAIN records a plan without running the explained statement. The formatted plan shows operators and estimates; it does not by itself show actual elapsed time, actual row counts, or parameter distributions. Explain output must be associated with the matching SQL, bind options, release, and statistics.

Decision rule: Explain the exact application statement under representative authorization and compilation settings; inspect the expensive operator and estimated cardinality, then compare against runtime evidence before changing SQL or indexes.

Worked examples and commands

Capture an explain plan for a read query

db2 "EXPLAIN PLAN FOR SELECT ORDER_ID, ORDER_DATE FROM APP.ORDERS WHERE CUSTOMER_ID = 10042 ORDER BY ORDER_DATE DESC"

Expected / interpretation: Explain tables must exist and the user needs explain access. EXPLAIN does not execute the SELECT.

Format the most recent explain instance

db2exfmt -d SAMPLE -1 -o orders_plan.exfmt

Expected / interpretation: Review operator tree, predicates, estimated rows, sort, table/index access, and object names.

Compare with a second predicate shape

db2 "EXPLAIN PLAN FOR SELECT ORDER_ID FROM APP.ORDERS WHERE STATUS = 'PENDING'"

Expected / interpretation: Compare only if both queries represent real workload and explain context is consistent.

Query execution architecture: SQL compilation produces an operator plan before execution

Plan choice and actual execution evidence must be compared to find estimate errors or resource bottlenecks.

Known issues, errors, fixes, and verification

EXPLAIN fails because explain tables are missing.

Likely cause: The explain schema objects were never created for the current authorization ID or database.

Fix: Install explain tables using the supported EXPLAIN.DDL script for this Db2 installation and grant only required access.

Verify: Repeat the EXPLAIN statement and run db2exfmt against the intended database.

Formatted plan contains no useful matching row or wrong query.

Likely cause: Plan selection was not scoped to the desired explain instance or schema, or the statement was compiled in another context.

Fix: Use EXPLAIN input identifiers, exact database, schema, statement, and bind settings; recapture the intended plan.

Verify: Check SQL text, explain timestamp, schema, and package/section identity in output.

A plan estimate is assumed to be actual runtime behavior.

Likely cause: Optimizer cardinality and cost are estimates, not execution measurements.

Fix: Use activity metrics, section actuals where supported, and representative application latency to verify the hypothesis.

Verify: Compare predicted and observed rows, I/O, CPU, sort, and elapsed time.

Hands-on lab: Read an access plan from SQL to returned rows

Objective: Locate the operator and estimate most likely to explain an observed query cost.

  1. Ensure explain tables exist in a lab database.
  2. Capture EXPLAIN PLAN for a representative SELECT.
  3. Format with db2exfmt and mark scans, joins, filters, sorts, and estimates.
  4. Compare plan estimates with activity/runtime evidence and state uncertainty.

Answer key: The analysis points to a specific plan operator and estimated row-flow issue, then names the runtime metric needed to prove impact.

Cleanup: Retain the explain file only in the lab workspace; drop explain tables only if created solely for the exercise.

Review question and answer

Question: What does EXPLAIN prove?

Answer: It records the optimizer-selected access plan in that compile context; it does not execute the query or measure actual runtime.
