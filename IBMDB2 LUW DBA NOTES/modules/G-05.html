Q Replication and SQL Replication Operations

Monitor capture/apply latency and exceptions, and reconcile target data after replication disruptions.

Level: Advanced · Effort: 3 hours
Prerequisites: C-05, E-03, and replication product design.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish Q Replication queues from SQL Replication staging.
  • Inspect capture/apply status and monitor tables.
  • Plan exception correction and target reconciliation.

How it works and when to use it

Q Replication uses Q Capture to read source log changes, IBM MQ queues to transport messages, and Q Apply to apply them at targets. SQL Replication uses Capture, change-data tables, and Apply subscriptions. Neither is a substitute for Db2 HADR failover: the target is a separate database with its own role, schema, and consistency rules. Capture and Apply are IBM Data Replication components with separately versioned commands and prerequisites.

Decision rule: Identify the exact replication product, program qualifier, source/target, control schema, queue manager or staging tables, and latency objective before operating it. Correct exceptions at the source/target contract level and reconcile actual data.

Worked examples and commands

Check IBM Data Replication command syntax

asnqccmd ?; asnqacmd ?; asnccmd ?; asnacmd ?

Expected / interpretation: These are IBM Data Replication program-control utilities, not base Db2 CLP commands; install and version must match the deployed replication product.

Inspect Q Capture monitor rows

db2 "SELECT COUNT(*) FROM ASN.IBMQREP_CAPMON"

Expected / interpretation: Use the configured control-table schema and review the product-level documented columns for latency, log position, queue depth, and timestamps.

Inspect SQL Replication apply monitor rows

db2 "SELECT COUNT(*) FROM ASN.IBMSNAP_APPLYMON"

Expected / interpretation: The table may use a configured ASN schema; use SQL Replication control-table ownership and current monitor documentation.

Replication architecture: Follow each change through capture, transport, and apply

Monitor each stage and prove target correctness independently of process state.

Known issues, errors, fixes, and verification

Capture is running but target data is stale.

Likely cause: Q Apply/Apply is stopped or backlogged, MQ queues are blocked, a subscription is inactive, or exceptions prevent apply.

Fix: Trace source capture position, transport queue or CD table, apply process state, and exception records in order; fix the first stalled stage.

Verify: Latency declines and target rows reconcile for a known source transaction marker.

Replication stops after a bulk utility operation.

Likely cause: Some Db2 utilities do not log row changes in the form Capture expects, or subscription restrictions were violated.

Fix: Use a replication-supported utility/path or planned target refresh and follow the product-specific resynchronization procedure.

Verify: Compare source/target data with a table-compare or deterministic reconciliation process.

Apply exceptions recur after manual correction.

Likely cause: Target schema, constraints, source key, transformation, or competing target writes remain incompatible.

Fix: Classify exception SQLCODE and row/key; correct the contract or conflict policy, then replay/reconcile using the replication product procedure.

Verify: Exception queue drains and source/target checksums or key-range counts match.

Hands-on lab: Trace replication latency end to end

Objective: Identify which replication stage owns a synthetic lag increase.

  1. Record Capture and Apply program identifiers, source/target, control schema, and timestamps.
  2. Read supported status output and monitor-table rows.
  3. Check MQ queue depth or SQL Replication staging backlog as applicable.
  4. Reconcile a synthetic transaction marker on the target and classify exceptions.

Answer key: The finding identifies source capture, transport, apply, or target conflict as the first stalled stage and includes data-correctness proof.

Cleanup: Stop test workload and remove only disposable replication subscriptions/markers using the product administration plan.

Review question and answer

Question: Why does a running Capture process not prove the target is current?

Answer: Capture may be ahead of a stalled transport or Apply process, and exceptions can prevent target changes from committing.
