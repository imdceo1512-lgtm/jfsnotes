Db2 Topology: Standalone, DPF, and pureScale

Identify database topology and learn how topology changes command scope, failure domains, and recovery operations.

Level: Advanced · Effort: 3 hours
Prerequisites: B-01 through B-05.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Identify single-partition, DPF, and pureScale characteristics.
  • Read topology metadata without changing it.
  • Check command scope and partition/member requirements.

How it works and when to use it

A standalone database has one database partition/member. DPF distributes database data across partitions and uses a catalog partition for coordination; partition-aware operations may affect selected or all partitions. pureScale has multiple members accessing shared data with cluster caching facilities and merged log behavior. Similar-looking commands can have different scope, and some maintenance/recovery tasks must start on specific members or coordinate all partitions.

Decision rule: Before running a topology-sensitive command, identify the deployment type, catalog partition/member, database partition list, and whether the operation is local, per partition, or global.

Worked examples and commands

Inspect Db2 node configuration on a partitioned instance

cat $HOME/sqllib/db2nodes.cfg

Expected / interpretation: The file lists partition host and logical port topology. Treat hostnames, ports, and member roles as sensitive operational metadata; compare with approved architecture.

Capture database-specific topology evidence

db2pd -alldbs
db2pd -db SAMPLE -applications

Expected / interpretation: Use supported db2pd sections to inspect database/member activity. Confirm exact options for the installed release and use output with the topology file.

Inspect member and host topology from the database

db2pd -db SAMPLE -dbptnmem

Expected / interpretation: Compare member numbers and host placement with the instance topology file and deployment inventory.

Topology architecture: Different Db2 layouts distribute data and coordination differently

Topology determines where data resides and which nodes participate in maintenance and recovery.

Known issues, errors, fixes, and verification

A utility runs successfully on one partition while other partitions remain unhealthy.

Likely cause: The command was issued with local scope or without the required catalog/all-partition clause.

Fix: Check the command’s documented topology scope and execute from the required partition with the intended partition list.

Verify: Collect status from all affected partitions/members and reconcile completion.

Restore/rollforward is started from a member absent from one image’s topology.

Likely cause: The selected member is not common to every backup image in the recovery chain.

Fix: Compare topology recorded in each image and run the operation from a member valid for all images, following IBM’s restore rules.

Verify: Complete recovery on the required topology and confirm database/member states converge.

A DPF host or logical port is mistaken for another partition.

Likely cause: The topology map is stale or logical partition IDs are not correlated with host and port.

Fix: Reconcile `db2nodes.cfg`, instance configuration, and current architecture inventory before any partition-specific action.

Verify: A read-only command reports the same host/member mapping as the approved topology.

Hands-on lab: Map a topology-sensitive recovery request

Objective: Select the correct scope and execution point from a synthetic DPF/pureScale design.

  1. Review standalone, DPF, and pureScale diagrams.
  2. Map partitions/members and identify the catalog partition or common member.
  3. Given a backup chain and target task, identify operation scope and required participants.
  4. Write two prechecks that prevent running on the wrong topology.

Answer key: The operator must prove topology, image compatibility, and command scope before recovery. A local success message does not establish all-member completion.

Cleanup: No live topology changes.

Review question and answer

Question: What must be checked before a topology-sensitive restore/rollforward?

Answer: The database topology, command scope, catalog partition/member requirements, and compatibility of every backup image in the chain.
