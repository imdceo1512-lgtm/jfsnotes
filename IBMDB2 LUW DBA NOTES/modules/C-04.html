Tablespaces, Storage Groups, Containers, and AUTORESIZE

Map database objects to storage, understand growth boundaries, and diagnose capacity problems.

Level: Intermediate · Effort: 2 hours
Prerequisites: B-03 and A-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Explain storage groups and automatic storage paths.
  • Read tablespace page size, type, and growth settings.
  • Identify the filesystem behind a tablespace and its capacity.

How it works and when to use it

A table space is the logical storage allocation for table data, indexes, or temporary work; its storage group and database storage paths determine physical placement. AUTORESIZE can extend a table space only while configured limits and underlying storage permit. A successful catalog setting does not guarantee free filesystem capacity. Keep page counts distinct from bytes and inspect both Db2 and host-level capacity.

Decision rule: Trace the object to its table space, table space to storage group/container or automatic-storage path, and path to the mounted filesystem. Resolve the limiting layer before increasing MAXSIZE or adding storage.

Worked examples and commands

Read table space definitions

db2 "SELECT TBSPACE, TBSPACETYPE, PAGESIZE, EXTENTSIZE, AUTORESIZE, MAXSIZE FROM SYSCAT.TABLESPACES ORDER BY TBSPACE"

Expected / interpretation: Use supported columns at the target release; MAXSIZE is not a filesystem free-space value.

Read live table space use

db2 "SELECT TBSP_NAME, TBSP_TYPE, TBSP_PAGE_SIZE, TBSP_TOTAL_PAGES, TBSP_USED_PAGES FROM TABLE(MON_GET_TABLESPACE(CAST(NULL AS VARCHAR(128)), -2)) AS T"

Expected / interpretation: The monitor values are pages; multiply by page size to estimate bytes and preserve member scope.

Inspect filesystem capacity for an identified path

df -h /db2data; df -i /db2data

Expected / interpretation: Run on the Db2 host and substitute the actual resolved mount. Inode exhaustion can block file creation before byte capacity reaches zero.

Storage architecture: Trace logical Db2 allocation to physical capacity

A capacity fix belongs at the layer that actually limits the next allocation.

Known issues, errors, fixes, and verification

SQL0289N says no more pages are available in the table space.

Likely cause: Table space reached a growth cap, all storage paths are full, or auto-resize is disabled/failing.

Fix: Trace the table space to physical paths and confirm capacity and mount health; add approved capacity or revise growth settings within policy.

Verify: Check MON_GET_TABLESPACE after the change, verify host free blocks/inodes, and retry a bounded lab insert.

AUTORESIZE is YES but the table space still cannot grow.

Likely cause: MAXSIZE, storage group paths, filesystem capacity, quota, permissions, or storage availability blocks extension.

Fix: Identify the effective cap and failing path; resolve host/storage issue or set a reviewed maximum with capacity owners.

Verify: Confirm next-extend capacity and a successful controlled extension; check diagnostics for path-specific errors.

Monitoring values appear implausibly small or large.

Likely cause: Page counts were reported as bytes or page size/member scope was ignored.

Fix: Read page size and units, aggregate only appropriate member rows, and state conversion formula.

Verify: Compare calculated size to tablespace properties and host allocation.

Hands-on lab: Trace a full table space to a filesystem

Objective: Determine whether Db2 growth limits or host capacity is the blocker.

  1. Select a table space and query its catalog and monitor properties.
  2. Convert used and total pages to bytes using the reported page size.
  3. Map the physical path and inspect blocks, inodes, mount state, and permissions.
  4. Propose a change only after identifying the constrained layer.

Answer key: The diagnosis names the logical limit, physical path, filesystem capacity, and evidence that distinguishes Db2 cap from host exhaustion.

Cleanup: Read-only lab; make no growth change without an approved capacity target.

Review question and answer

Question: What does AUTORESIZE=YES fail to guarantee?

Answer: It does not guarantee unlimited growth or available host storage; configured maximum, path availability, quotas, and filesystem capacity still apply.
