Availability and Change Practicum: HADR, Upgrade, and Rollback

Choose a safe path across a planned outage, a primary-site failure, and a forward-only software upgrade.

Level: Senior DBA practicum · Effort: 4 hours
Prerequisites: G-02/G-03 and I-02/I-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Select unforced takeover versus forced failover from current state and outage evidence.
  • Plan target-level upgrade gates and identify forward-only boundaries.
  • Prove client service after role or software change.

How it works and when to use it

Scenario one is a planned primary-host maintenance window with a synchronized standby. Scenario two is an unexpected primary outage where the standby receive/replay positions and peer-window state determine possible data loss. Scenario three is a Db2 upgrade where db2ckupgrade finds a prerequisite and database upgrade cannot be reversed in place. The senior DBA must distinguish high availability from upgrade, separate product automation from database state, and document data-loss/rollback authority.

Decision rule: For planned work, require eligible HADR state and unforced takeover. For an outage, choose forced takeover only with an approved data-loss decision and proven primary isolation. For upgrade, stop until target-level precheck, tested backup, HADR compatibility, and recovery path are accepted.

Worked examples and commands

Review roles and state on both HADR endpoints

db2pd -db SAMPLE -hadr

Expected / interpretation: Capture both hosts with synchronized timestamps, sync mode, connection state, and receive/replay positions.

Review target-version upgrade precheck

/opt/ibm/db2/V12.1/bin/db2ckupgrade SAMPLE -l /secure/db2ckupgrade.log

Expected / interpretation: Resolve every error and review warnings before instance upgrade.

Run the planned takeover only in a lab

db2 takeover hadr on db SAMPLE

Expected / interpretation: Unforced role switch requires an eligible pair; validate client redirection and application writes afterward.

Availability/change decision tree: Different conditions require different role and upgrade paths

Do not use failover to bypass planned eligibility or use a software rollback assumption after forward-only database upgrade.

Known issues, errors, fixes, and verification

Operator proposes forced takeover while original primary may still be accepting writes.

Likely cause: Primary isolation and standby log currency are unproven; concurrent primaries risk split-brain and divergence.

Fix: Use cluster/network evidence to establish primary failure/isolation and obtain the authorized data-loss decision; do not issue command from a single status screen.

Verify: One writable primary remains, standby role/state is correct, client routing moves, and transaction marker shows accepted loss bound.

Planned takeover fails with SQL1770N.

Likely cause: HADR state, replay delay, peer-window, upgrade, or licensing prerequisites make standby ineligible.

Fix: Read reason code and fix eligibility or reschedule; do not convert it to forced takeover merely to meet the window.

Verify: Unforced lab takeover completes and both endpoints report stable roles.

Upgrade precheck fails after the change window begins.

Likely cause: Deprecated setting, invalid object, log position, unsupported feature, or insufficient space was not cleared before outage.

Fix: Abort before instance/database upgrade, preserve source level and backup, repair prerequisite, and reschedule.

Verify: Target-level precheck passes on a clone with the same topology and HADR state.

Hands-on lab: Senior DBA availability/change decision exercise

Objective: Defend a failover and upgrade plan from a time-limited scenario packet.

  1. Read current HADR state/positions and identify whether the outage is planned or unplanned.
  2. State takeover command choice, possible data loss, primary isolation proof, and client checks.
  3. Run db2ckupgrade on a clone and document each warning/error gate.
  4. Identify the irreversible upgrade point, tested restore path, package checks, and new backup requirement.
  5. Write the owner-approved stop/go decision and service acceptance tests.

Answer key: Planned work uses unforced takeover; forced failover is gated by isolation and data-loss approval; upgrade is gated by clean target precheck and a tested recovery path. Service acceptance includes client routing and business transaction checks.

Cleanup: No production role changes or upgrades; use a paired lab/clone.

Review question and answer

Question: What evidence must precede a forced HADR takeover?

Answer: Confirmed primary failure/isolation, standby state and log position, authorized data-loss decision, client-routing plan, and split-brain prevention.
