DPF and pureScale Operational Models

Recognize distributed partition and shared-data cluster topology and apply the right command scope.

Level: Advanced · Effort: 2 hours
Prerequisites: B-06, F-08, E-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish DPF data placement from pureScale shared-data members.
  • Inspect member/partition topology with supported tools.
  • Account for topology in maintenance, recovery, and incident commands.

How it works and when to use it

DPF partitions database data across partition servers using distribution maps and inter-partition communication. pureScale members access shared database storage and coordinate through cluster caching facilities. A standard single-member instance differs from both. Command scope, failure behavior, backup/restore, and workload placement depend on topology. Never edit topology metadata by hand or assume a command ran globally because it was issued on one host.

Decision rule: Identify topology before any maintenance: inspect db2nodes.cfg and LIST DBPARTITIONNUMS for DPF, db2instance -list for pureScale, and use db2pd member scope to inspect engine state. Follow the topology-specific change and recovery procedure.

Worked examples and commands

List database partition numbers

db2 connect to SAMPLE; db2 list dbpartitionnums

Expected / interpretation: A pureScale database reports one database partition number; do not infer it is a single-member instance.

Inspect partition topology file on Linux/UNIX

cat $HOME/sqllib/db2nodes.cfg

Expected / interpretation: Read-only inspection only; never edit db2nodes.cfg manually during normal operations or on Windows.

List pureScale members and CFs

db2instance -list

Expected / interpretation: Run with required authority on a server host; output reports member and cluster caching facility states.

Topology architecture: Data placement and shared-data membership differ

Topology determines which nodes own data, which state to inspect, and how maintenance or recovery is coordinated.

Known issues, errors, fixes, and verification

A command affects only the local member when the operator expected cluster-wide scope.

Likely cause: Member scope was omitted or a deprecated/global option was assumed.

Fix: Use documented -member all syntax or the appropriate database command scope and verify output on each member.

Verify: Collect per-member state and ensure every intended member appears in the result.

DPF node number is confused with pureScale member number.

Likely cause: Both topologies use member/partition terminology but represent different data placement and cluster designs.

Fix: Identify deployment feature from license/topology/configuration before interpreting identifiers or partitioning output.

Verify: Cross-check db2nodes.cfg, LIST DBPARTITIONNUMS, db2instance output, and architecture inventory.

Manual topology-file edit causes startup or partition inconsistencies.

Likely cause: Node topology was changed outside supported Db2 topology commands and database metadata workflows.

Fix: Stop edits; use the documented add/drop member or partition procedure and open a support case if metadata already diverged.

Verify: Compare topology commands, cluster manager state, and database partition data after the supported repair.

Hands-on lab: Classify a Db2 deployment topology

Objective: Identify which architecture is present and how a monitor command should be scoped.

  1. Collect db2level and instance deployment documentation.
  2. Run LIST DBPARTITIONNUMS and inspect db2nodes.cfg read-only on a DPF candidate.
  3. Run db2instance -list on a pureScale candidate.
  4. Run db2pd -member all on a supported topology and list all visible member results.

Answer key: The report distinguishes a single-member instance, DPF data partitions, and pureScale members/CFs; command scope is stated explicitly.

Cleanup: Read-only topology lab.

Review question and answer

Question: Why is LIST DBPARTITIONNUMS alone insufficient to identify pureScale topology?

Answer: A pureScale database can report one database partition number; use instance-level member and CF state as well.
