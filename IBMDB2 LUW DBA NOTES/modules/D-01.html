Authentication Architecture and Operating-System Boundaries

Trace identity from client credentials through the server authentication plug-in and host account/group resolution.

Level: Intermediate · Effort: 2 hours
Prerequisites: A-02 and B-02.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Separate authentication from authorization.
  • Identify client, server, and group-resolution boundaries.
  • Collect identity evidence without exposing credentials.

How it works and when to use it

Authentication validates who connected; authorization determines what that identity can do. Db2 LUW uses operating-system or configured authentication mechanisms at connection time. The database manager configuration can assign authentication responsibility to the server, client, or a supported external mechanism. Host groups can map to Db2 authorities, so NSS/LDAP resolution and service account differences matter. Never put passwords in command history, logs, or screenshots.

Decision rule: When a connection fails, establish the actual client identity and server endpoint first; then inspect authentication configuration and group resolution on the configured authority host before changing database grants.

Worked examples and commands

Inspect authentication-related Db2 manager settings

db2 get dbm cfg | grep -i -E "AUTHENTICATION|SRVCON_AUTH|GROUP_PLUGIN"

Expected / interpretation: Capture the exact server configuration and release; a client-side display may not show the active server settings.

Resolve a service identity on Linux

id appsvc; getent passwd appsvc; getent group db2grp1

Expected / interpretation: Run in the relevant host/container context and compare interactive versus service identity.

Confirm the authenticated database identity

db2 "VALUES CURRENT USER, SESSION_USER, SYSTEM_USER"

Expected / interpretation: These registers help distinguish session identity from the authenticated system identity; test through the same client path as the application.

Identity path architecture: A connection crosses identity and authorization boundaries

Find the failed boundary using the same identity and connection path as the workload.

Known issues, errors, fixes, and verification

A valid OS account cannot connect to Db2.

Likely cause: Authentication setting, account lock/expiry, group plug-in lookup, client mechanism, or server endpoint differs from the assumed path.

Fix: Capture SQLCODE and server diagnostic tokens; verify effective DBM CFG, configured auth host, identity state, and name-service lookup.

Verify: Reconnect using the application’s service identity through the same DNS name, port, and driver.

Interactive login succeeds while the application fails.

Likely cause: The application process uses another identity, credential source, group cache, or connection pool.

Fix: Inspect service manager/container identity and secret injection; recycle a test pool only after correcting identity mapping.

Verify: Record SESSION_USER and SYSTEM_USER from an application-originated test connection.

Credentials appear in shell history or process output.

Likely cause: Password was supplied as a command-line argument.

Fix: Rotate the exposed credential and use approved secret storage or an interactive/driver-managed credential path.

Verify: Review shell history and process logging retention and confirm the new secret is used.

Hands-on lab: Trace an application identity

Objective: Map one test connection to its host and Db2 identities.

  1. Record the client process identity, DSN/alias, DNS endpoint, and Db2 server version.
  2. Inspect relevant server authentication and group plug-in configuration.
  3. Resolve the service user and groups on the configured authentication host.
  4. Run identity-register SQL through the application connection and compare results.

Answer key: The map names the client identity, server endpoint, authentication authority, resolved groups, and returned Db2 identity; credentials are not recorded.

Cleanup: Remove temporary identity probes and redact secret-bearing traces.

Review question and answer

Question: Does successful authentication prove that a user can SELECT a table?

Answer: No. Authentication proves identity; object privilege, authority, role/group membership, and package rules determine access.
