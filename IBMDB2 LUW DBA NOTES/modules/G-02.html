HADR Architecture, Roles, States, and Synchronization Modes

Read HADR role/state, log shipping and replay position, synchronization guarantees, and takeover readiness.

Level: Advanced · Effort: 2.5 hours
Prerequisites: F-01, F-02, and G-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Explain primary and standby log flow.
  • Compare SYNC, NEARSYNC, ASYNC, and SUPERASYNC trade-offs.
  • Read HADR state and lag as a set of measurements.

How it works and when to use it

The primary writes logs locally and ships them to one or more standby databases, where they are received and replayed. Synchronization mode controls how commit acknowledgment relates to standby log receipt or disk persistence; lower latency generally reduces protection against network/site loss. PEER, REMOTE_CATCHUP, LOCAL_CATCHUP, and disconnected states describe different positions in the log lifecycle. A standby role alone does not prove current log currency.

Decision rule: Choose mode and peer-window behavior from measured network latency, required data-loss tolerance, and transaction impact; use receive/replay positions and state transitions to determine readiness, not role alone.

Worked examples and commands

Inspect HADR status

db2pd -db SAMPLE -hadr

Expected / interpretation: Check role, state, sync mode, connection status, log positions, and heartbeat at the correct member.

Read HADR metrics with member scope

db2 "SELECT MEMBER, HADR_ROLE, HADR_STATE, HADR_SYNCMODE, HADR_CONNECT_STATUS, STANDBY_RECV_REPLAY_GAP FROM TABLE(MON_GET_HADR(NULL)) AS H"

Expected / interpretation: Column availability and semantics are release-sensitive; inspect MON_GET_HADR reference for the installed level.

Read effective HADR configuration

db2 get db cfg for SAMPLE show detail

Expected / interpretation: Review HADR host/service/instance, timeout, synchronization, peer window, and target list on both endpoints.

HADR log-flow architecture: Primary commit and standby replay are separate stages

Monitor receive and replay progress separately because a healthy network does not guarantee replay capacity.

Known issues, errors, fixes, and verification

The pair is connected but replay lag is growing.

Likely cause: Standby log replay throughput is below log generation or standby storage is slow.

Fix: Compare primary log generation, standby receive and replay positions, CPU, and log-device latency; size replay resources based on evidence.

Verify: Under representative load, lag returns to a stable bounded value and the standby remains in expected state.

Commit latency increases after selecting stronger synchronization.

Likely cause: Network round-trip and standby log I/O are on the commit path for that mode.

Fix: Measure network and log-device latency and select the strongest mode that meets both data-loss and workload objectives.

Verify: Compare transaction latency and recovery gap over a representative test window.

Peer window causes blocked commits during a network partition.

Likely cause: Primary is waiting for standby reconnection or peer-window expiry to protect consistency.

Fix: Follow the approved incident decision tree; understand peer-window and synchronization compatibility before changing settings or forcing takeover.

Verify: Confirm the selected mode/state and data-loss decision with both cluster and database evidence.

Hands-on lab: Interpret HADR state under load

Objective: Evaluate whether a standby is current enough for the stated recovery objective.

  1. Capture db2pd -hadr output on primary and standby with synchronized timestamps.
  2. Capture MON_GET_HADR metrics by member and repeat at a fixed interval.
  3. Compare receive position, replay position, gap trend, state, and workload log rate.
  4. State whether evidence meets the scenario’s takeover/readiness threshold.

Answer key: Readiness is based on state, log currency, connection, sync mode, and trend; the threshold is tied to the business RPO.

Cleanup: No HADR configuration changes.

Review question and answer

Question: What does PEER state prove, and what does it not prove?

Answer: It indicates the pair is synchronized at a defined point under the configured mode; it does not by itself prove client redirection, site dependencies, or a successful service failover.
