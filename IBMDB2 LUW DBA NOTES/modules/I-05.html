Federation, Wrappers, Servers, User Mappings, and Nicknames

Query remote data through Db2 Federation while checking pushdown, credentials, transaction boundaries, and network cost.

Level: Advanced · Effort: 2 hours
Prerequisites: D-03, C-03, H-02.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Explain wrapper/server/user mapping/nickname roles.
  • Inspect nickname query plans for remote pushdown.
  • Diagnose remote schema, credentials, and availability dependencies.

How it works and when to use it

A wrapper implements access to a data source; a server object describes the remote endpoint; a user mapping maps local identity to remote credentials; a nickname represents a remote object locally. The optimizer determines which predicates and operators can be pushed to the source. If a selective filter is evaluated locally, a large remote result can cross the network. Federation adds source availability, credentials, type mapping, and transaction semantics to every query path.

Decision rule: Confirm the data source and wrapper are supported/licensed, secure the user mapping, refresh remote metadata, explain the query for SHIP/pushdown behavior, and benchmark source and network impact before production use.

Worked examples and commands

Inventory configured federation servers

db2 "SELECT SERVERNAME, WRAPNAME, SERVERTYPE, SERVERVERSION FROM SYSCAT.SERVERS"

Expected / interpretation: Catalog columns vary with server options/release; inspect SYSCAT.SERVERS and redact endpoints in shared output.

Inspect local nickname definitions

db2 "SELECT NICKNAME, TABSCHEMA, SERVERNAME FROM SYSCAT.NICKNAMES WHERE TABSCHEMA = 'APP'"

Expected / interpretation: Use schema-qualified nickname inventory and verify its target server and remote object.

Explain a nickname query

db2 "EXPLAIN PLAN FOR SELECT ORDER_ID FROM APP.REMOTE_ORDERS WHERE CUSTOMER_ID = 10042"; db2exfmt -d SAMPLE -1 -o remote_plan.exfmt

Expected / interpretation: Check the operator location and SHIP boundary; if the optimizer cannot push down a filter, remote rows may be fetched locally.

Federation architecture: Local SQL is decomposed across a remote boundary

A plan that filters remotely can reduce transfer; unsupported operations may run locally over transferred rows.

Known issues, errors, fixes, and verification

A federated query downloads many rows and filters them locally.

Likely cause: Predicate/operator cannot be pushed down due to function mapping, type/collation semantics, or server capability metadata.

Fix: Inspect explain plan and remote capabilities; adjust compatible expression or catalog metadata and retest data semantics.

Verify: Plan shows selective work at source and measured network bytes/latency decline without changing results.

Nickname query fails after remote password rotation.

Likely cause: User mapping contains stale credentials or remote account policy changed.

Fix: Rotate the secret in the approved credential path and update mapping without exposing passwords in scripts/logs.

Verify: Test as the intended local user and confirm remote identity and least privilege.

Remote rows return with unexpected type or collation behavior.

Likely cause: Wrapper mapping or source SQL semantics differ from local Db2 assumptions.

Fix: Review nickname column types/options and pushdown behavior; test boundary values, collations, and NULL semantics.

Verify: Compare target output to authoritative source queries for edge cases.

Hands-on lab: Trace a federated SELECT

Objective: Confirm which operations run remotely and which run on the federation server.

  1. Record wrapper, server, nickname, user mapping, and remote object details.
  2. Explain a selective remote query and identify SHIP/RETURN operators.
  3. Compare source row count with rows transferred and local result count.
  4. Test one type/collation edge case and one remote authorization failure in the lab.

Answer key: The report names each federation object, local/remote execution boundary, credential mapping, and correctness/performance verification.

Cleanup: Drop only lab nicknames and mappings; securely remove any temporary secrets.

Review question and answer

Question: What does a SHIP operator tell you in a federated plan?

Answer: It marks a data-flow boundary where operations are sent to or returned from a remote source; plan location reveals pushdown behavior.
