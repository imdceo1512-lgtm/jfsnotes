Recovery Objectives and Backup Design

Turn business recovery goals into image, log, retention, capacity, security, and rehearsal decisions.

Level: Intermediate · Effort: 2 hours
Prerequisites: F-01 and service criticality basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Translate RPO and RTO into measurable recovery design.
  • Identify dependencies required to restore and open a database.
  • Estimate whether a proposed backup and restore schedule meets objectives.

How it works and when to use it

RPO limits acceptable data loss; RTO limits restoration time. A recovery design needs a usable base image, all required incremental/delta images, required logs, and platform dependencies such as paths, key material, software level, credentials, and application validation. Backup completion time is not restore time. Account for retrieval, decompression/decryption, log application, database validation, and application cutover.

Decision rule: Start with the required recoverable point and service deadline, then choose backup cadence, log archive throughput, retention, copy isolation, restore capacity, and rehearsal interval. A design fails if any dependency cannot meet the objective.

Worked examples and commands

Review backup history as an inventory input

db2 list history backup all for SAMPLE

Expected / interpretation: Use history timestamps and types to reconcile with the scheduler and storage inventory. A history row is not proof that every image object is readable.

Estimate nominal active-log disk requirement

(LOGPRIMARY + LOGSECOND) * (LOGFILSIZ + 2) * 4096 bytes

Expected / interpretation: Use effective settings; treat LOGSECOND=-1 separately. This estimates active-log allocation, not total archive-retention space. Include archive outage and workload-growth headroom.

Estimate archive capacity from measured log generation

awk -v rate_mib_min=120 -v retention_h=24 'BEGIN {printf "archive_GiB=%.1f\n", rate_mib_min*retention_h*60/1024}'

Expected / interpretation: Replace the sample rate and retention with measured peak values, then add concurrency, failed-archive backlog, and safety headroom.

Recovery dependency architecture: RPO and RTO require more than a backup file

Any missing or slow dependency can constrain the recovery point or duration.

Known issues, errors, fixes, and verification

The policy meets the backup schedule but misses the RPO.

Likely cause: The gap between recoverable images and archived logs exceeds the business loss tolerance, or log retrieval is unreliable.

Fix: Measure image completion and archive lag; define the recoverable point and retain required artifacts off-host.

Verify: During a controlled drill, recover within the approved RPO and reconcile application transactions.

A restore completes technically but service misses the RTO.

Likely cause: Retrieval, rollforward, validation, or client cutover time was omitted from the estimate.

Fix: Time each stage, provision a realistic target, automate only safe repeatable steps, and revise the capacity plan.

Verify: Repeat the end-to-end drill and compare full service-restoration time with the RTO.

An image exists but cannot be decrypted or retrieved.

Likely cause: Key material, storage credentials, vendor library, or archive permissions were not retained with the recovery package.

Fix: Version and protect key-recovery steps; confirm the restore role can retrieve every artifact.

Verify: Restore on a clean test host using only the documented package and role.

Hands-on lab: Design an RPO/RTO-backed recovery policy

Objective: Produce a recovery design that can be proved by a timed rehearsal.

  1. Define acceptable data loss and outage duration for a synthetic workload.
  2. Map the base image, image chain, logs, keys, access, software level, and target capacity.
  3. Estimate retrieval, restore, rollforward, verification, and application validation time.
  4. Identify the weakest dependency and revise the plan.

Answer key: The plan identifies the exact image and log chain, retrieval locations, credentials/keys, time convention, target capacity, and acceptance query. Unmeasured estimates are labeled assumptions and trigger a rehearsal.

Cleanup: No database changes; use synthetic values only.

Review question and answer

Question: What proves an RTO claim?

Answer: A timed end-to-end rehearsal that includes retrieval, restore, log application, database checks, and application acceptance.
