Incident Scope, Timeline, Baseline, and Evidence Quality

Build a reliable incident record that ties impact, time, hypotheses, and evidence to the right Db2 environment.

Level: Intermediate · Effort: 1.5 hours
Prerequisites: A-01 through A-05 and B-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Write an impact and time-window statement.
  • Capture environment identity and synchronized timestamps.
  • Separate observation, hypothesis, action, and outcome.

How it works and when to use it

An operational incident begins with impact scope, affected service, start/end estimates, and the source of those times. Evidence must identify host, instance, database/member, client, timezone, and collection time. Db2, host, driver, and application clocks can differ. A useful timeline separates observed facts from interpretation and records each change with an owner and result. Baselines let the responder tell a current anomaly from normal workload variation.

Decision rule: Start read-only. Capture enough evidence to preserve current state before intervention; choose the smallest test that can disprove the leading hypothesis and record its effect.

Worked examples and commands

Capture Db2 release and instance identity

db2level; db2 get instance; db2 list active databases

Expected / interpretation: Run as the intended instance environment and retain host/time identity with the output.

Capture UTC timestamp and OS identity

date -u +%Y-%m-%dT%H:%M:%SZ; hostname -f; id

Expected / interpretation: Use UTC consistently in the shared incident timeline while preserving source timezone.

Record database identity and config

db2 "VALUES CURRENT SERVER, CURRENT USER"; db2 get db cfg for SAMPLE

Expected / interpretation: Store only approved configuration evidence; redact secrets and sensitive endpoint details before sharing.

Incident evidence flow: Preserve context before testing a hypothesis

Context and baseline make the evidence comparable across teams and systems.

Known issues, errors, fixes, and verification

Teams disagree about when the incident began.

Likely cause: Each system uses a different clock or timezone, and event times were copied without source context.

Fix: Record UTC and source timezone, validate host time synchronization, and identify the first user-visible impact separately from first alert.

Verify: Correlate one shared request or error identifier across application, network, and Db2 timestamps.

A diagnostic bundle cannot be tied to the affected database.

Likely cause: Host, instance, database alias, member, or client context was omitted.

Fix: Capture db2level, instance, current server, application identity, and member scope alongside each command result.

Verify: A second responder can reproduce the same read-only query from the recorded context.

A remediation changes the evidence before it is captured.

Likely cause: Restart, cleanup, force application, or config change was performed before the initial state was preserved.

Fix: Capture relevant state and diagnostic interval first unless immediate safety requires intervention; document that exception.

Verify: Timeline contains before/after evidence, change owner, exact action, and observed outcome.

Hands-on lab: Assemble a first-response evidence sheet

Objective: Produce a compact incident record that another DBA can continue.

  1. State user impact, affected service, first known failure, and confidence.
  2. Record host, Db2 release, instance, database, member, client identity, and UTC collection time.
  3. Gather read-only config and diagnostic evidence before making changes.
  4. List observations separately from hypotheses and name the next discriminating test.

Answer key: The handoff is reproducible and distinguishes facts, assumptions, actions, and outcomes with timestamps and environment scope.

Cleanup: Redact credentials and sensitive payloads before sharing the evidence sheet.

Review question and answer

Question: What makes diagnostic evidence reusable by another responder?

Answer: It records source, time, environment identity, scope, and exact command/query, and separates measured facts from interpretation.
