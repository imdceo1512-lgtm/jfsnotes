Integrity, Dependencies, and Safe Object Maintenance

Resolve integrity pending and invalid-object conditions with controlled validation and dependency-aware checks.

Level: Intermediate · Effort: 2 hours
Prerequisites: C-02 and C-05.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Identify integrity and check-pending states.
  • Use SET INTEGRITY only after correcting underlying data problems.
  • Verify dependencies, object validity, and accepted row counts after maintenance.

How it works and when to use it

Bulk operations and certain DDL can defer constraint checking or leave objects requiring validation. SET INTEGRITY validates specified tables against constraints and can leave them in a pending state if violations exist. Exception tables can retain violating rows for correction. Integrity resolution does not prove dependent packages and applications work; those require separate validity and application checks.

Decision rule: First read utility and state evidence; identify the exact constraint and violating rows; preserve rejected data; correct source or target rows; validate in a disposable or controlled change window; then verify object dependencies and application behavior.

Worked examples and commands

Inspect table status and constraints

db2 "SELECT TABSCHEMA, TABNAME, STATUS, TYPE FROM SYSCAT.TABLES WHERE TABSCHEMA = 'APP' AND TABNAME = 'ORDERS_LAB'"; db2 "SELECT CONSTNAME, TYPE, ENFORCED FROM SYSCAT.TABCONST WHERE TABSCHEMA = 'APP' AND TABNAME = 'ORDERS_LAB'"

Expected / interpretation: Use the table status and constraint metadata as clues; exact status flags vary by object and release.

Validate a corrected lab table

db2 "SET INTEGRITY FOR APP.ORDERS_LAB IMMEDIATE CHECKED"

Expected / interpretation: Only after offending rows have been corrected or isolated; the statement can fail again when violations remain.

Check dependent package validity

db2 "SELECT PKGSCHEMA, PKGNAME, VALID, OPERATIVE FROM SYSCAT.PACKAGES WHERE PKGSCHEMA = 'APP'"

Expected / interpretation: Prepare or rebind only the affected packages using the application owner’s release procedure.

Integrity recovery flow: Keep failing rows visible until the target is safe

A successful integrity command is one checkpoint; object and application validation complete the maintenance workflow.

Known issues, errors, fixes, and verification

SQL0668N reason code indicates the table cannot be accessed.

Likely cause: The table is in a pending state, often after a utility or integrity operation.

Fix: Use the reason code and utility history to select the required recovery/integrity action; do not guess with repeated SET INTEGRITY.

Verify: Read table state, rerun the exact validating action, and test a controlled SELECT.

SET INTEGRITY fails because constraint violations remain.

Likely cause: Rows still violate a check, unique, or referential rule, or parent/child validation order is wrong.

Fix: Identify violating keys, use an approved exception-table/staging process, correct data, and validate parent dependencies first.

Verify: Query for duplicates/orphans/invalid values, reconcile exceptions, then rerun integrity validation.

Table becomes accessible but an application package fails.

Likely cause: DDL or object replacement invalidated dependent packages, or signature/privilege assumptions changed.

Fix: Identify affected package dependencies and use the application’s controlled rebind/redeploy process.

Verify: Check package validity and run application smoke tests through the actual driver and service account.

Hands-on lab: Resolve a staged integrity violation

Objective: Practice detecting and repairing a constraint failure before making data available.

  1. Create a disposable table with a check constraint and load a valid plus invalid synthetic row into staging.
  2. Record the violating input and accepted/rejected counts.
  3. Correct or isolate invalid rows and run SET INTEGRITY on the lab target.
  4. Verify constraints, target counts, package validity, and a read query.

Answer key: The repair preserves rejected-row evidence, validates all declared rules, reconciles row counts, and separately confirms dependent package and application validity.

Cleanup: Drop only disposable objects and files after retaining the lab answer.

Review question and answer

Question: What should be proved after SET INTEGRITY succeeds?

Answer: The target is accessible, constraints hold, accepted/rejected counts reconcile, dependent packages remain valid, and the application can read the repaired data.
