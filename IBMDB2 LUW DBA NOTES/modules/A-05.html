Linux Networking, DNS, Ports, and Time

Trace the client-to-server path and verify name resolution, routing, listener, firewall, and clock assumptions.

Level: Beginner · Effort: 2 hours
Prerequisites: A-01 through A-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Trace a hostname to an address and route.
  • Check local listener and client reachability evidence.
  • Explain how time skew disrupts incident correlation and secure connections.

How it works and when to use it

A successful DNS lookup does not prove that packets reach the Db2 host; a listening port does not prove the application can authenticate or connect. Separate name resolution, route, firewall, socket listener, TLS handshake, authentication, and database authorization. Time synchronization matters for certificate validity, HADR event order, and evidence correlation. Use the same hostname and port the client actually uses.

Decision rule: Test each network layer from the affected client and server, recording address/port and timestamp. Do not open a firewall or change SSL settings until the failed layer is identified.

Worked examples and commands

Resolve the server name and inspect route

getent ahosts db2server.example.net
ip route get 192.0.2.25

Expected / interpretation: The address is an example. Compare the resolved address with the expected endpoint and route; DNS can return multiple addresses or stale records.

Check the local listener and clock

ss -lntp
timedatectl status

Expected / interpretation: Confirm the expected port is listening on the intended interface and time synchronization is healthy. `ss -p` may require elevated visibility.

Test the configured Db2 TCP port from the client host

nc -vz -w 3 db2server.example.net 50000

Expected / interpretation: A successful TCP connection proves reachability to that host and port only; it does not prove Db2 authentication or database availability.

Connection flow: Test network and Db2 layers separately

The first failed boundary narrows diagnosis; later layers should not be changed until earlier evidence is sound.

Known issues, errors, fixes, and verification

Hostname resolves but client receives connection timeout.

Likely cause: Route, firewall, security group, NAT, or wrong resolved address blocks the path.

Fix: Compare client route and server-side packet/listener evidence; request only the specific approved path change.

Verify: Repeat a bounded connection test from the same client and confirm the intended server logs the attempt.

TCP connection succeeds but Db2 connection fails.

Likely cause: TLS, authentication, client catalog/driver, database alias, or authorization fails above the network layer.

Fix: Capture the complete Db2/driver message, then test TLS, identity, catalog and database authorization as separate layers.

Verify: A controlled client connection succeeds and the server sees the expected identity and database.

Certificate appears expired or not yet valid on one endpoint.

Likely cause: Clock drift or certificate lifecycle problem causes validity checks to fail.

Fix: Verify synchronized clocks first; then inspect certificate chain, hostname, and validity with approved tools.

Verify: TLS handshake succeeds with normal certificate validation and no clock offset.

Hands-on lab: Build a client-to-Db2 connection fault tree

Objective: Find the first failed network or database layer from synthetic traces.

  1. Resolve the hostname from client and server.
  2. Inspect route and listener for the configured Db2 port.
  3. Classify supplied outcomes as DNS, network, TLS, authentication, or authorization failure.
  4. Write the next low-risk test and evidence to collect.

Answer key: Test in order: resolution→route→TCP listener→TLS→authentication→database alias/connect→authorization. A TCP result alone is not proof of a valid Db2 session.

Cleanup: No firewall or certificate changes; use test endpoints only.

Review question and answer

Question: What does a successful `ss -lntp` result prove?

Answer: Only that a local socket is listening on the reported address/port at capture time; it does not prove remote reachability or successful Db2 authentication.
