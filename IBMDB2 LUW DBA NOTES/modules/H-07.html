Workload Management, I/O, and Maintenance Tuning

Use workload classes and service metrics to isolate noisy neighbors, utility contention, and persistent I/O limits.

Level: Advanced · Effort: 2 hours
Prerequisites: C-06, E-06, and H-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Inventory workload/service-class configuration.
  • Correlate I/O wait and utility work to an affected class.
  • Evaluate thresholds and maintenance timing against service objectives.

How it works and when to use it

Db2 Workload Management classifies connections and activities and can control or monitor work through service classes, workloads, work action sets, and thresholds. Poorly designed controls can queue critical work or cause unexpected rejection. Utilities compete for CPU, memory, log bandwidth, and storage I/O with business queries. Maintenance schedules should be selected from measured benefit and conflict patterns.

Decision rule: First identify which workload and resource are competing; test classification and control rules in nonproduction; use thresholds to enforce a stated policy, not to hide an unmeasured bottleneck.

Worked examples and commands

Inventory service classes

db2 "SELECT * FROM SYSCAT.SERVICECLASSES FETCH FIRST 10 ROWS ONLY"

Expected / interpretation: Catalog columns are release-specific; inspect SYSCAT.SERVICECLASSES and include only supported columns.

Measure service subclass workload

db2 "SELECT * FROM TABLE(MON_GET_SERVICE_SUBCLASS(NULL, NULL, -2)) AS S FETCH FIRST 10 ROWS ONLY"

Expected / interpretation: Review the MON_GET_SERVICE_SUBCLASS reference for valid returned fields; preserve member scope.

Review ongoing utilities and reorganization

db2pd -db SAMPLE -utilities; db2pd -db SAMPLE -reorgs

Expected / interpretation: These are current-state views. Correlate utility phase and resource use with service latency before rescheduling.

Workload control architecture: Classify first, then apply a measured resource policy

The control is useful only when classification and success criteria match the real workload.

Known issues, errors, fixes, and verification

Critical reporting work queues behind a batch workload.

Likely cause: Both workloads share a service class or a work action/threshold routes them unexpectedly.

Fix: Trace workload mapping and service-class hierarchy; adjust classification or resource policy in a controlled test.

Verify: Report workload meets its latency target while batch throughput and fairness remain acceptable.

REORG or LOAD causes a foreground latency spike.

Likely cause: Maintenance consumes shared I/O, CPU, log, or lock resources during peak demand.

Fix: Measure the maintenance phase and foreground waits; reschedule, throttle where supported, or select a lower-impact option.

Verify: Repeat representative maintenance and business load with a defined latency/throughput threshold.

A WLM threshold blocks work unexpectedly.

Likely cause: Threshold scope, action, or service-class membership does not match the intended class.

Fix: Review the threshold definition and affected activity evidence; disable or alter only through controlled change process.

Verify: Test one allowed and one constrained workload and inspect classification plus threshold event output.

Hands-on lab: Map a noisy-neighbor incident to workload policy

Objective: Identify whether one class or utility is driving another class’s latency.

  1. Inventory service classes and workload mappings.
  2. Capture service-subclass metrics for the same interval as application latency.
  3. Inspect utility state and host I/O/CPU for overlap.
  4. Propose a nonproduction classification or scheduling change and define fairness criteria.

Answer key: The result names the contending workload/resource and tests the policy effect on both the constrained and protected workloads.

Cleanup: Revert the lab WLM change and stop test utility activity.

Review question and answer

Question: Why should thresholds not be added before workload classification is verified?

Answer: An incorrect class mapping can throttle the wrong work and turn an isolated slowdown into a service outage.
