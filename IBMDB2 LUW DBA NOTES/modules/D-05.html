Security Auditing, Row and Column Controls, and Sensitive Data

Apply auditable policies and data restrictions with evidence that matches the organization’s control objectives.

Level: Intermediate · Effort: 2 hours
Prerequisites: D-02 and data classification policy.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Separate audit collection from authorization controls.
  • Apply and commit an audit policy in a lab.
  • Explain where LBAC or row/column access control fits.

How it works and when to use it

Db2 auditing records configured events for later analysis; it does not itself prevent unauthorized access. Database audit policies are created by SECADM and associated with database entities. Instance-level db2audit administration is separate. LBAC labels or row/column access controls restrict rows or columns according to policy. Data classification, audit retention, access to audit files, event selection, and operational overhead must be designed together.

Decision rule: Select events from a defined control question, avoid capturing data values unless approved, protect audit output, and test both allowed and denied access under representative identities.

Worked examples and commands

Create and associate a focused audit policy

db2 "CREATE AUDIT POLICY APPSEC_AUDIT CATEGORIES CHECKING STATUS FAILURE, SECMAINT STATUS BOTH ERROR TYPE NORMAL"; db2 "AUDIT DATABASE USING POLICY APPSEC_AUDIT"; db2 "COMMIT"

Expected / interpretation: Run connected to the intended disposable database as SECADM. The audit policy records selected checks; it does not grant or deny table access.

Define a row permission and enable row access control

db2 "CREATE PERMISSION APP.ORDERS_OWNER ON APP.ORDERS FOR ROWS WHERE CREATED_BY = SESSION_USER ENFORCED FOR ALL ACCESS ENABLE"; db2 "ALTER TABLE APP.ORDERS ACTIVATE ROW ACCESS CONTROL"

Expected / interpretation: This assumes APP.ORDERS has a CREATED_BY character column containing authorization IDs. Define and test the permission before activation; test as the intended application users.

Mask a sensitive column and enable column access control

db2 "CREATE MASK APP.SALARY_MASK ON APP.EMPLOYEE FOR COLUMN SALARY RETURN CASE WHEN VERIFY_GROUP_FOR_USER(SESSION_USER, 'PAYROLL') = 1 THEN SALARY ELSE DECIMAL(0,9,2) END ENABLE"; db2 "ALTER TABLE APP.EMPLOYEE ACTIVATE COLUMN ACCESS CONTROL"

Expected / interpretation: This assumes APP.EMPLOYEE.SALARY is DECIMAL(9,2) and PAYROLL is a Db2-resolvable group. Confirm the target data type and test both authorized and masked identities.

Inspect and extract archived instance audit records

db2audit describe; db2audit extract delasc

Expected / interpretation: Extract after the relevant instance audit log has been archived. Db2 writes category-specific delimited files to the configured archive location; secure and rotate them under the retention policy.

Control architecture: Enforcement and evidence work together

The control prevents or allows access; the audit facility records selected events about that decision.

Known issues, errors, fixes, and verification

Audit policy exists but expected events are absent.

Likely cause: Policy was not associated with the entity, change was not committed, category did not include the event, or audit output is unavailable.

Fix: Check SYSCAT.AUDITPOLICIES/AUDITUSE, commit status, configured category, audit state, and data/archive path.

Verify: Generate a controlled event and locate its record in the expected database audit trail.

Sensitive values appear in audit extracts.

Likely cause: EXECUTE WITH DATA or contextual capture includes parameter/input values beyond the approved scope.

Fix: Restrict categories and data capture, secure existing extracts, and follow incident/privacy retention procedure.

Verify: Run a synthetic parameterized statement and inspect the extract for values before enabling broader capture.

A table is audited but users can still read it.

Likely cause: Auditing records events; it does not authorize or block access.

Fix: Use privileges, roles, LBAC, or row/column access control to enforce access, then audit the relevant checks.

Verify: Test permitted and denied identities separately and confirm both enforcement and required event records.

Row access control returns no rows immediately after activation.

Likely cause: No enabled row permission was defined before activation, so the default permission denies access.

Fix: Define and enable the intended permission, activate row access control, and review any dependent packages before rollout.

Verify: Test representative allowed and denied identities and confirm both row sets match the policy.

A column mask is defined but users still see the original values.

Likely cause: Column access control is inactive, the mask is disabled or invalid, or the test identity meets the unmasked branch.

Fix: Check mask status and expression type, activate column access control, then test as identities on both sides of the policy.

Verify: Compare the sensitive column as an authorized identity and an ordinary application identity.

Hands-on lab: Design an auditable access control

Objective: Demonstrate policy selection, association, commit, and a controlled verification event.

  1. Write a one-sentence control question and identify the exact event category.
  2. Create and associate the policy in a disposable database using SECADM.
  3. Commit, generate one synthetic denied access attempt, and archive/extract according to the lab procedure.
  4. Verify the event and separately verify access enforcement.

Answer key: The design states what event is captured, who can read the output, how long it is retained, and which separate grant/control actually blocks access.

Cleanup: Remove the lab policy association and policy only after retaining the synthetic result.

Review question and answer

Question: What is the difference between auditing and LBAC?

Answer: Auditing records configured activity; LBAC enforces row or column access based on security labels.
