Db2 Agents, EDUs, Memory Areas, and Work Units

Relate connections and transactions to agent work, engine threads, memory consumption, and saturation.

Level: Advanced · Effort: 2.5 hours
Prerequisites: B-01 and monitoring fundamentals.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish application connections, agents, and EDUs.
  • Read targeted Db2 process evidence.
  • Connect memory/agent pressure to workload behavior.

How it works and when to use it

Db2 uses EDUs to perform database work; agents service application requests, while other EDUs handle logging, page cleaning, monitoring, and background activity. Connection pooling can lower connect overhead while increasing the number of idle sessions or concentrating concurrent work. Memory is divided among shared and private areas. Agent saturation, memory pressure, and a slow statement are different diagnoses and need different evidence.

Decision rule: Use a database-scoped capture, map application handles and EDU IDs, and compare concurrent demand with configured/observed limits before changing agent or memory settings.

Worked examples and commands

Inspect application handles and clients

db2pd -db SAMPLE -applications

Expected / interpretation: Capture application handle, status, client identity, and coordinator information. Compare active versus idle connections and note the sample time.

Inspect EDU state and memory consumers

db2pd -edus
db2pd -db SAMPLE -memsets

Expected / interpretation: Use EDU and memory-set output to form a hypothesis; options and fields can vary by release. Compare multiple captures before concluding a leak or saturation.

Inspect active transaction and log-space use

db2pd -db SAMPLE -transactions

Expected / interpretation: Match the application handle and transaction state to the connection evidence; a large log-space value can explain log pressure.

Engine work architecture: Connections consume agents and shared/private engine resources

Connection limits, agent capacity, and memory usage interact but are not interchangeable counters.

Known issues, errors, fixes, and verification

Connections wait although CPU is low.

Likely cause: Agent availability, locks, log I/O, or remote/client waits may be limiting progress.

Fix: Map the waiting applications to agent/EDU and lock/log state; increase limits only after finding the constrained resource.

Verify: Repeat the same connection workload and confirm wait duration and queue depth fall without exhausting memory.

Memory grows after enabling a larger connection pool.

Likely cause: More concurrent agents/private memory or package-cache demand is created by the pool.

Fix: Measure active/idle pool size and Db2 memory areas; cap or tune the pool based on workload concurrency and memory budget.

Verify: Track peak memory and throughput under the same connection pattern.

An EDU with high CPU is terminated to reduce load.

Likely cause: The EDU may be executing required work or may not be mapped to the suspected application.

Fix: Capture EDU/application mapping and current statement before any intervention; cancel only through an approved application-specific process.

Verify: Confirm the intended unit of work ends, transaction outcome is known, and database consistency remains normal.

Hands-on lab: Map connection pool behavior to agent demand

Objective: Distinguish connection count from active work.

  1. Capture `db2pd -db SAMPLE -applications` and `db2pd -edus` under idle pool conditions.
  2. Repeat while a controlled workload runs.
  3. Compare active requests, idle connections, EDU state, and memory sets.
  4. Recommend one pool limit and one Db2 metric to watch.

Answer key: Connection count alone does not equal active workload; the pool should be sized to application concurrency and database resource limits.

Cleanup: Stop the lab client workload and return the pool to its original setting.

Review question and answer

Question: Why should a DBA map an EDU to an application before acting?

Answer: EDUs include background work and can service different applications; a PID/thread by itself does not identify the business request.
