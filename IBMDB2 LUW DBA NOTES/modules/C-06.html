Statistics, RUNSTATS, REORGCHK, and REORG Operations

Refresh optimizer evidence and decide when physical reorganization is justified.

Level: Intermediate · Effort: 2 hours
Prerequisites: C-03, C-04, and query-plan basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Choose targeted RUNSTATS scope.
  • Interpret REORGCHK as evidence rather than an automatic command.
  • Schedule and verify table reorganization with workload impact understood.

How it works and when to use it

RUNSTATS writes catalog statistics consumed by the optimizer. Stale or incomplete statistics can produce poor access paths; collecting the wrong scope can consume resources and change plans. REORGCHK evaluates statistics using formulas and thresholds; it indicates candidates, not universal mandates. REORG rewrites table or index organization and can require substantial I/O, space, locks, and a maintenance window.

Decision rule: Collect fresh statistics after substantial data change or reorganization; inspect a representative explain plan; reorganize only when evidence shows physical organization is limiting performance and the access impact is acceptable.

Worked examples and commands

Collect table and index statistics

db2 "RUNSTATS ON TABLE APP.ORDERS WITH DISTRIBUTION AND DETAILED INDEXES ALL"

Expected / interpretation: This can be resource intensive; choose columns/distribution scope for the workload and run in an approved window.

Check current reorganization indicators

db2 "REORGCHK CURRENT STATISTICS ON TABLE APP.ORDERS"

Expected / interpretation: Current statistics avoids an implicit refresh; stale statistics weaken the conclusion.

Inspect an active reorganization

db2pd -db SAMPLE -reorgs

Expected / interpretation: Run on the Db2 host; empty output can mean no active reorg, not that a historical reorg never occurred.

Maintenance decision flow: Refresh evidence before expensive physical maintenance

Plan behavior and measured workload determine whether statistics or physical reorganization is the relevant intervention.

Known issues, errors, fixes, and verification

RUNSTATS fails with authorization or object errors.

Likely cause: Wrong database/schema/table, disconnected session, or insufficient utility authority.

Fix: Verify connection and qualified object, then use a role with the documented RUNSTATS authority.

Verify: Check command completion messages and compare catalog statistics timestamps/values.

Query plan worsens immediately after RUNSTATS.

Likely cause: New statistics changed optimizer estimates, or the chosen collection scope is incomplete for skew/correlation.

Fix: Capture before/after EXPLAIN and runtime metrics; gather workload-relevant distribution/column-group stats and review access path.

Verify: Compare equivalent parameter values and workload under controlled conditions.

REORG is proposed but cannot run within the window.

Likely cause: The expected duration, space, access mode, or log/utility constraints were not assessed.

Fix: Estimate with representative volume, check disk and transaction requirements, choose supported online/offline mode, and schedule with rollback plan.

Verify: Monitor utility progress and post-reorg space/statistics/plan behavior.

Hands-on lab: Evidence-based maintenance decision

Objective: Decide whether stale statistics or physical disorder is the primary issue.

  1. Capture the query plan and current RUNSTATS history for a lab table.
  2. Run targeted RUNSTATS, then compare EXPLAIN output.
  3. Run REORGCHK against current statistics and record the recommendation.
  4. Only in disposable data, run REORG and gather post-maintenance statistics.

Answer key: RUNSTATS is selected when optimizer information is stale; REORG requires physical and workload evidence plus a safe window; the post-action plan and runtime are compared.

Cleanup: No production reorganization; restore lab data if the exercise altered it.

Review question and answer

Question: Does a REORGCHK recommendation prove that REORG will fix a slow query?

Answer: No. It identifies potential physical improvement from catalog statistics; confirm the plan, workload, access impact, space, and measured result.
