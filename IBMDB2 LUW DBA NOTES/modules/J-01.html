Bash and ksh for Db2 Operations

Write shell commands that preserve arguments, return codes, safe paths, and the Db2 instance environment.

Level: Advanced · Effort: 2 hours
Prerequisites: A-02 and B-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Quote paths and SQL arguments safely.
  • Handle return codes, signals, and pipeline failures.
  • Distinguish Bash features from portable POSIX/ksh behavior.

How it works and when to use it

Administrative shell scripts cross shell, Db2 CLP, and SQL parsers. Quoting must preserve intended SQL and paths. Pipelines can hide Db2 failures unless pipefail is enabled; source the correct instance profile and verify DB2INSTANCE. Destructive commands should require allowlisted targets, explicit dry-run, and separate authorization.

Decision rule: Validate inputs, quote expansions, capture status immediately, and stop later steps after failure. Test shell syntax and failure behavior in a disposable environment.

Worked examples and commands

Enable strict Bash error handling

set -euo pipefail

Expected / interpretation: Bash-specific; do not assume this works identically in POSIX sh or every ksh implementation.

Run a read-only Db2 command and preserve its exit code

db2 -x "VALUES CURRENT SERVER"; rc=$?; printf "db2_rc=%s
" "$rc"; exit "$rc"

Expected / interpretation: Capture status immediately; do not use an unchecked pipeline that replaces Db2 return code.

Validate a script without running it

bash -n ./collect_db2.sh

Expected / interpretation: Syntax checking does not prove command semantics or target identity.

Command execution path: The shell passes arguments through CLP to SQL

Each layer can change meaning or status; validate the target and preserve failure signals.

Known issues, errors, fixes, and verification

A script reports success after db2 failed.

Likely cause: A later command overwrote the Db2 exit status or pipeline failure was ignored.

Fix: Capture status immediately or handle pipefail, then propagate the failure explicitly.

Verify: Use a lab command expected to fail and confirm the script exits before subsequent actions.

SQL quoting changes the submitted predicate.

Likely cause: Shell expansion or nested quotes altered the SQL string.

Fix: Use a quoted heredoc or variable-safe approach and test with a harmless SELECT before mutation.

Verify: Capture submitted SQL in a lab and confirm keys/predicate match.

Script connects to the wrong database or instance.

Likely cause: Inherited profile, current user, DB2INSTANCE, or catalog alias differs from expected host context.

Fix: Load the intended profile, allowlist host/alias, and print identity before write commands.

Verify: Query CURRENT SERVER and CURRENT USER and compare with approved target manifest.

Hands-on lab: Harden a read-only DBA shell command

Objective: Wrap a Db2 query with explicit environment, output, and error handling.

  1. Set restrictive umask and source intended instance profile.
  2. Validate alias against a short allowlist.
  3. Run a harmless identity query and record return code.
  4. Force a lab failure and prove the script stops.

Answer key: The script quotes arguments, proves target identity, propagates failure, and does not place secrets in command history.

Cleanup: Remove only the temporary lab script and output.

Review question and answer

Question: Why can set -e alone be insufficient for Db2 automation?

Answer: Some conditions and pipelines have special shell error behavior; explicitly capture and test critical command status.
