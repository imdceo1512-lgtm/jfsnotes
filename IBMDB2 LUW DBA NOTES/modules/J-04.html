Testable and Idempotent Administrative Automation

Design repeatable runbooks that converge on intended state, handle partial failure, and stop on unknown results.

Level: Advanced · Effort: 2 hours
Prerequisites: J-01 through J-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Separate plan, apply, and verify phases.
  • Make safe operations idempotent or detect prior completion.
  • Inject failures to validate rollback and checkpoint behavior.

How it works and when to use it

Automation can fail after a server accepts a request but before the client records success. Idempotence means a repeated run reaches the same intended state without repeating harmful side effects; not every Db2 command is idempotent. A safe workflow records operation identity, preconditions, checkpoint, state transition, and postcondition. Retries must inspect current state and distinguish not-started, completed, failed, and unknown.

Decision rule: Default to dry-run, make a plan from observed state, require reviewed authorization for mutation, execute one bounded step, and verify its postcondition before moving to the next step.

Worked examples and commands

Review current state before changing it

db2 get db cfg for SAMPLE show detail

Expected / interpretation: Compare current and delayed values to desired state; do not blindly reapply a setting.

Separate syntax/plan review from execution

db2 -tvf change.sql -z change.out

Expected / interpretation: Use only a reviewed lab file; retain return code and inspect output for every statement result.

Reconcile after a timed-out operation

db2 "VALUES CURRENT SERVER"; db2 get db cfg for SAMPLE show detail

Expected / interpretation: Reconnect and query actual state before deciding whether a retry is safe.

Idempotent runbook flow: Each action is guarded by a state checkpoint

A timeout enters an unknown-state branch that must be resolved before retry.

Known issues, errors, fixes, and verification

A retry applies a non-idempotent action twice.

Likely cause: Automation assumes a timeout means the command did not execute.

Fix: Record an operation ID and query the exact postcondition before retry; use a manual unknown-state gate when state cannot be proven.

Verify: Inject a client timeout after server acceptance and show a second run does not duplicate work.

Partial run leaves later steps executing against inconsistent state.

Likely cause: Runbook lacks checkpoints or stops only on the final aggregate status.

Fix: Gate every dependent step on its postcondition, use explicit stop-on-error behavior, and define a compensation per completed stage.

Verify: Fail each stage in turn and confirm later stages do not run.

Dry-run output differs from the command actually executed.

Likely cause: Plan generation and apply path use separate variable expansion or mutable inputs.

Fix: Generate one immutable command plan, review/hash it, and apply the exact reviewed values.

Verify: Compare plan and execution manifest IDs and record actual server-side state.

Hands-on lab: Failure-inject a multi-step maintenance runbook

Objective: Show checkpoints and safe resumption after each possible failure.

  1. Create a dry-run plan with target identity and desired state.
  2. Add a checkpoint and postcondition for each lab action.
  3. Simulate failure before, during, and after one action.
  4. Resume by querying state and reconciling rather than rerunning blindly.

Answer key: Every retry has a proven current state and operation identity; unknown completion pauses for review.

Cleanup: Restore lab state from the original snapshot after recording the failure cases.

Review question and answer

Question: What does idempotence require when a command times out?

Answer: A retry must inspect and reconcile actual state first; timeout alone does not prove that the operation failed.
