Database Creation, Activation, Connections, and Configuration Scope

Create a controlled database, connect to the correct alias, and distinguish configuration scope and effective values.

Level: Intermediate · Effort: 3 hours
Prerequisites: B-01 and B-02; isolated instance.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Create a lab database with explicit code page/territory and page size.
  • Separate DBM CFG from DB CFG.
  • Interpret dynamic versus delayed configuration changes.

How it works and when to use it

CREATE DATABASE initializes catalogs, initial table spaces, logs, and a directory entry. Code page and territory are design choices that cannot be changed after creation. Database-manager configuration belongs to the instance; database configuration belongs to a specific database. Some settings take effect dynamically, others after deactivate/reactivate or instance restart. `GET ... SHOW DETAIL` helps compare current and delayed values. SQL1363W indicates that some requested values did not take effect immediately.

Decision rule: Before changing a parameter, check its scope, dynamic behavior, required authority, activation boundary, and workload impact in the installed release documentation.

Worked examples and commands

Create a disposable UTF-8 lab database

db2 create database LABDB using codeset UTF-8 territory US pagesize 8192

Expected / interpretation: Use only a new lab alias and valid codepage/territory combination. Database creation may run configuration advice and automatic maintenance; inspect resulting configuration before teaching with it.

Read and update database configuration

db2 get db cfg for LABDB show detail
db2 update db cfg for LABDB using locktimeout 30
db2 get db cfg for LABDB show detail

Expected / interpretation: `locktimeout` is a database parameter. Compare current and delayed values and explain when a database reactivation is required; do not assume every setting changes immediately.

Verify the connected database identity

db2 connect to LABDB; db2 "VALUES CURRENT SERVER"; db2 connect reset

Expected / interpretation: The returned server name confirms which database the CLP session reached; reset the connection before switching targets.

Configuration scope map: Instance settings and database settings have different owners and activation behavior

The scope and effective value must be identified before interpreting a configuration change.

Known issues, errors, fixes, and verification

`SQL1363W` appears after a configuration update.

Likely cause: One or more parameters do not support immediate dynamic change.

Fix: Use `GET DB CFG ... SHOW DETAIL` to identify delayed values; schedule the documented deactivate/reactivate or restart boundary.

Verify: Read the parameter after the required activation boundary and run a functional post-check.

Database creation fails with a codepage/collation error.

Likely cause: The selected codeset, territory, or collation combination is invalid.

Fix: Choose a supported combination from IBM’s release/operating-system documentation; do not create the production database with guessed locale values.

Verify: Recreate only in the lab and query database configuration/catalog metadata to confirm the chosen values.

A setting changes in one database but not another.

Likely cause: The command targeted a different alias or the parameter belongs to the instance rather than the database.

Fix: Confirm current instance and alias, then use the correct DBM CFG or DB CFG command.

Verify: Read configuration from each explicitly named target and record effective values.

Hands-on lab: Create and configure LABDB

Objective: Practice database creation and a parameter lifecycle check.

  1. Confirm `db2 get instance` and `db2level`.
  2. Create LABDB with explicit UTF-8/territory and page size.
  3. Read DBM and DB configuration; update a low-risk lab parameter.
  4. Observe immediate/delayed values and perform the documented activation step if required.

Answer key: The learner distinguishes instance and database scope and uses SHOW DETAIL plus release documentation to determine when the new value is active.

Cleanup: Drop only LABDB after disconnecting and confirming its lab identity.

Review question and answer

Question: What does SQL1363W mean after an UPDATE DB CFG command?

Answer: The command was processed, but at least one requested parameter did not change dynamically and requires the documented activation boundary.
