Cross-Platform Migration and Data Portability

Select backup/restore or logical movement based on platform family, Db2 level, data types, and application dependencies.

Level: Advanced · Effort: 2 hours
Prerequisites: C-05, F-05, and I-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Check platform-family and release compatibility before physical restore.
  • Use db2look and data movement tools for logical portability.
  • Reconcile schemas, code pages, routines, packages, and data after transfer.

How it works and when to use it

Physical backup/restore compatibility is constrained by Db2 release, operating-system/platform family, endianness, architecture, compression/encryption libraries, and topology. Logical movement through DDL and export/import/load can cross some physical boundaries but does not automatically move every dependency or preserve identical behavior. User-defined routines, sequences, grants, identity settings, collations, code pages, LOB/XML data, and application drivers need separate checks.

Decision rule: Choose physical restore only when IBM’s platform and version matrix allows the exact source/target pair. Otherwise build DDL and move data logically, then validate row counts, constraints, encoding, packages, and application semantics.

Worked examples and commands

Extract application DDL

db2look -d SAMPLE -e -z APP -o app_ddl.sql

Expected / interpretation: DDL output is a starting point; review unsupported clauses, owners, tablespaces, routines, grants, and ordering before execution.

Export a bounded logical data set

db2 "EXPORT TO /secure/migrate/orders.del OF DEL SELECT ORDER_ID, STATUS FROM APP.ORDERS"

Expected / interpretation: Protect exported data and preserve character encoding; include LOB/XML handling if the source schema needs it.

Check physical image header before a planned restore

db2ckbkp -h /db2backup/IMAGE_FILE

Expected / interpretation: Header inspection reports source metadata but does not prove cross-platform restore compatibility or full image integrity.

Migration path decision: Choose physical or logical movement from compatibility evidence

The chosen transfer path must include non-table dependencies and a target-side acceptance test.

Known issues, errors, fixes, and verification

Restore rejects an image from another OS or hardware family.

Likely cause: Source and target are in different supported platform families, or compression/encryption library is unavailable.

Fix: Follow IBM compatibility matrix; use a supported cross-platform method or logical DDL/data transfer.

Verify: Restore a representative copy on the target platform and validate code page, data, and application behavior.

Data imports but strings are corrupted or truncated.

Likely cause: Code page, delimiter, character encoding, LOB handling, or column mapping differs.

Fix: Record source/target code pages and data types; use explicit file modifiers/mappings and test Unicode edge cases.

Verify: Compare byte/character lengths, checksums, representative international characters, and row counts.

Schema/data moved but application fails.

Likely cause: Routines, sequences, grants, triggers, package dependencies, collations, or external libraries were omitted.

Fix: Reconcile complete schema inventory and deploy external/client dependencies with versioned configuration.

Verify: Run package rebind and end-to-end application tests under the target service identity.

Hands-on lab: Rehearse a logical migration

Objective: Transfer a small synthetic schema and prove both structural and data correctness.

  1. Extract DDL and create a dependency-ordered schema on a compatible lab target.
  2. Export a defined synthetic row set with explicit data format and encoding.
  3. Import or load into staging and reconcile source/target counts and key ranges.
  4. Validate constraints, grants, routines, packages, and application query results.

Answer key: Migration acceptance includes DDL, data, dependent objects, code page/encoding, grants, and business-level output—not only utility success.

Cleanup: Remove only disposable target schema and synthetic files.

Review question and answer

Question: When is logical export/import preferable to restoring an image?

Answer: When the exact physical restore source/target combination is unsupported or when a schema-level migration is required, provided all logical dependencies are rebuilt and validated.
