Connections, Applications, Agents, Transactions, and Long-Running Work

Find the application that owns work, distinguish idle from executing activity, and identify transaction age and waits.

Level: Intermediate · Effort: 1.5 hours
Prerequisites: E-03 and SQL transaction basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Map application handles to client identity and application name.
  • Distinguish idle connections from executing or queued work.
  • Use transaction age and lock evidence before taking action.

How it works and when to use it

A connection can be pooled and idle while still consuming resources or holding an open unit of work. An application handle identifies a connection; an activity identifies a submitted operation. The coordinator agent executes on behalf of work, and parallel work can use more agents. Long-running units of work can retain locks and log records even when the current statement is idle. Cancelling or forcing an application can roll back work and affect clients.

Decision rule: Identify the exact handle, user, application, client, member, UOW age, activity state, and lock/wait evidence. Contact the owning workload and estimate rollback impact before interrupting it.

Worked examples and commands

List applications with detail

db2 list applications show detail

Expected / interpretation: Correlate application handle, auth ID, client, and status. Idle does not mean harmless if a unit of work remains open.

Query live connections

db2 "SELECT MEMBER, APPLICATION_HANDLE, APPLICATION_NAME, CLIENT_USERID, UOW_START_TIME FROM TABLE(MON_GET_CONNECTION(NULL, -2)) AS C"

Expected / interpretation: Check target-level columns and keep member scope; null UOW start time can mean no active unit of work.

See currently executing/queued activities

db2 "SELECT MEMBER, APPLICATION_HANDLE, ACTIVITY_STATE, ACTIVITY_TYPE FROM TABLE(MON_GET_ACTIVITY(NULL, -2)) AS A"

Expected / interpretation: This returns current activities, not completed history. Use a targeted event monitor for past work.

Work ownership flow: Connection, transaction, and activity are separate states

Do not confuse a pooled idle connection with a completed transaction.

Known issues, errors, fixes, and verification

A connection is idle but log space remains pinned.

Likely cause: The client left an open transaction after its last statement or is waiting for user input while holding locks.

Fix: Correlate UOW start time, transaction state, locks, and application owner; ask the owner to commit/rollback or use a controlled timeout policy.

Verify: Confirm the UOW ends and pinned-log/lock symptoms clear without harming other requests.

A long statement is killed without understanding rollback cost.

Likely cause: Elapsed time alone was treated as proof of a runaway query.

Fix: Inspect activity state, rows/CPU progress, lock waits, execution plan, and owning application before cancellation.

Verify: Monitor rollback completion and compare service impact; document the cancellation reason and owner.

Application handle cannot be found in current output.

Likely cause: The connection ended, moved member scope, or was queried after the incident window.

Fix: Capture repeated samples and use event-monitor or application logs for historical evidence.

Verify: Correlate using client address, auth ID, application name, timestamp, and statement identifiers.

Hands-on lab: Triage a long-running unit of work

Objective: Identify whether a synthetic transaction is active, idle, blocked, or safe to finish.

  1. Capture application list and MON_GET_CONNECTION for the lab database.
  2. Find the oldest UOW and identify its user, app name, client, member, and handle.
  3. Query live activity and lock evidence for that handle.
  4. Choose owner contact, wait, cancellation, or intervention and state rollback risk.

Answer key: The action is based on UOW/activity/lock state and ownership, not duration alone.

Cleanup: End the synthetic transaction with an explicit commit or rollback.

Review question and answer

Question: Why can an IDLE application still be operationally important?

Answer: It can have an open UOW and retain locks or log records while waiting on the client.
