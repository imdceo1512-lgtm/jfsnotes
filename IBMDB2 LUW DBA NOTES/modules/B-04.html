CLP, Command Files, Terminators, and Safe Workflows

Use Db2 CLP predictably in interactive sessions and scripts, preserving return codes and target identity.

Level: Intermediate · Effort: 2 hours
Prerequisites: B-02 and basic shell quoting.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Select CLP options for SQL command files.
  • Explain terminators and the CLP back-end connection.
  • Capture command output and return status safely.

How it works and when to use it

The CLP front end launches commands and a back-end process maintains the connection. `TERMINATE` ends the back end and refreshes directory cache. SQL terminators matter in command files; `-t` uses semicolon by default, while `-td@` selects `@`. `-v` echoes commands and `-f` reads a file. Shell quoting is a separate layer from SQL quoting. A command file can partially apply changes before a later statement fails, so scripts need clear transaction and error behavior.

Decision rule: Use read-only commands and a disposable database for examples. In a script, choose one terminator explicitly, stop on errors, record environment/return code, and do not assume a CLP file is atomic.

Worked examples and commands

Run a SQL file terminated by semicolons

db2 -tvf inspect.sql

Expected / interpretation: The CLP echoes statements, uses the default semicolon terminator, and reads the file. Review the file before execution and use a lab database for changes.

Run statements terminated by @ then refresh CLP

db2 -td@ -vf setup.sql
db2 terminate

Expected / interpretation: `-td@` sets `@` as statement terminator; `-v` echoes and `-f` reads the file. `TERMINATE` closes the CLP back end. This does not roll back statements already committed.

Capture the command-file process exit status

db2 -tvf inspect.sql; rc=$?; printf "CLP_RC=%s\n" "$rc"

Expected / interpretation: The shell exit status helps automation detect failure. Inspect the Db2 SQLCODE and command output as well; a script can contain more than one statement.

CLP execution flow: Shell parsing, CLP parsing, SQL execution, and status return

A failure can occur at each parser/execution layer; preserve the exact command and message.

Known issues, errors, fixes, and verification

CLP reports a statement cut off or continues reading.

Likely cause: The file terminator does not match the configured CLP terminator, or a delimiter appears inside a literal.

Fix: Set the terminator with `-t`/`-td` and inspect the exact file; use the chosen delimiter consistently.

Verify: Run a harmless SELECT file first and confirm exactly the intended statements execute.

The command returns success while an earlier SQL statement failed.

Likely cause: A wrapper script ignores the CLP return code or continues after an error.

Fix: Capture `$?` immediately, use shell strict/error handling, and inspect all SQL messages; stop before dependent actions.

Verify: Inject one controlled lab error and confirm the wrapper exits nonzero and skips later steps.

A catalog change is invisible to the current session.

Likely cause: CLP or directory cache still holds the previous directory state.

Fix: Issue `db2 terminate` to refresh the CLP session; use documented instance cache refresh only if necessary.

Verify: List node/database directories in a new CLP session and confirm the intended alias.

Hands-on lab: Build a safe CLP inspection file

Objective: Run a read-only file with explicit terminator and error capture.

  1. Create `inspect.sql` with two SELECT statements and `@` terminators.
  2. Run it using `db2 -td@ -vf inspect.sql` in LABDB.
  3. Introduce a harmless invalid object name and observe the return code/output.
  4. Update a shell wrapper to stop before any subsequent operation.

Answer key: The delimiter is explicit; the wrapper preserves Db2 messages and nonzero status; the invalid statement prevents later actions.

Cleanup: Delete the lab file and disconnect; no database changes.

Review question and answer

Question: Why does `TERMINATE` matter after catalog changes?

Answer: It ends the CLP back-end session and refreshes its cached directory view.
