Db2 LUW Architecture: Instances, Databases, Members, and Agents

Map Db2 logical boundaries and the process path from client request to database work.

Level: Intermediate · Effort: 2.5 hours
Prerequisites: Linux process and network basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish instance, database, member, EDU, and application.
  • Trace a client request through the engine.
  • Identify topology-dependent scope before issuing commands.

How it works and when to use it

An instance owns database-manager configuration and engine processes; a database has its own catalogs, configuration, logs, and table spaces. A client connection is represented by an application and serviced by engine dispatchable units (EDUs), including agents. In DPF, database partitions own portions of data and work; in pureScale, multiple members access a shared database with cluster caching facilities. These layouts change command scope, log streams, and failure boundaries.

Decision rule: Before diagnosis, record instance, database alias, member/partition, client, and time window. Never infer a topology from a database name or one process listing.

Worked examples and commands

Record active Db2 copy and instance level

db2level
db2ilist

Expected / interpretation: `db2level` identifies the active Db2 code level; `db2ilist` lists local instances. Run under the intended environment and distinguish installed copies from the copy used by this instance.

Inspect EDUs and database applications

db2pd -edus
db2pd -db SAMPLE -applications

Expected / interpretation: Use the first output for engine threads/EDUs and the second for database applications. Capture timestamps and correlate handles with the incident; do not treat every EDU as a client connection.

List active databases for the current instance

db2 list active databases

Expected / interpretation: This reports databases active in the current instance environment; it does not list every cataloged alias.

Db2 request architecture: Client work crosses instance, database, application, and engine boundaries

The mapping prevents conflating users, applications, engine threads, and topology members.

Known issues, errors, fixes, and verification

A DBA inspects the wrong instance while the alias name looks correct.

Likely cause: `DB2INSTANCE` or profile selects a different instance/copy than expected.

Fix: Record `db2level`, `db2ilist`, environment, and `db2 get instance`; reconnect only after target identity is confirmed.

Verify: A known database alias, instance owner, and server endpoint match the change or incident record.

Many EDUs are mistaken for many connected users.

Likely cause: An application can use multiple EDUs; background engine tasks also appear in process data.

Fix: Correlate `db2pd -applications` handles with EDU IDs and client details.

Verify: Application count, EDU count, and workload evidence are described separately.

A DPF/pureScale symptom is diagnosed using single-partition assumptions.

Likely cause: The operator ignores member/partition scope and topology-specific work or log streams.

Fix: Read `db2nodes.cfg` and release-supported topology/monitor outputs; identify the catalog partition or member requirement for the operation.

Verify: The command’s documented scope matches the target partition/member and all relevant nodes are represented.

Hands-on lab: Trace a client request through Db2

Objective: Map a synthetic connection to the process and topology that serves it.

  1. Capture instance and Db2 level.
  2. Use `db2pd -db SAMPLE -applications` and `db2pd -edus` in a lab.
  3. Map one application handle to its EDU and client identity.
  4. Draw the topology path for standalone, DPF, and pureScale cases.

Answer key: Keep instance, database, member/partition, application handle, EDU, and client endpoint as distinct identifiers; they answer different operational questions.

Cleanup: No state changes.

Review question and answer

Question: Why is an EDU count not a connection count?

Answer: Engine EDUs include database agents and background tasks, and a client request can involve more than one EDU.
