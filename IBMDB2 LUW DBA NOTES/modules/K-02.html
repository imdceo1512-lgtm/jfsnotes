Recovery Practicum: Full, Incremental, Point-in-Time, and Tablespace

Select an exact image chain and practice recovery-state handling under wrong-target and missing-log traps.

Level: Senior DBA practicum · Effort: 3 hours
Prerequisites: F-03 through F-09; G-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Select the correct full plus incremental/delta chain.
  • Distinguish restore, rollforward, and tablespace recovery.
  • Reconcile data at a declared recovery point.

How it works and when to use it

The recovery packet contains one full image, a cumulative incremental, a later delta, archived logs, and a separate tablespace image. The target objective is a stated timestamp and RPO. A wrong image or missing required log can produce an incomplete or unusable database. Full database PIT recovery returns all recoverable objects to a consistent point; tablespace recovery has separate state and dependencies. Preserve original artifacts and work on an isolated target.

Decision rule: Verify image metadata, database identity, chain timestamps, platform compatibility, log availability, storage paths, and target objective before restore. Use automatic incremental restore only when the correct chain can be selected; stop at the approved point and validate business data.

Worked examples and commands

Inventory backup images

db2 list history backup all for SAMPLE; db2ckbkp -h /db2backup/IMAGE_FILE

Expected / interpretation: History and header identify candidates; validate image readability and chain separately.

Restore a full base and required incremental chain

db2 restore db SAMPLE incremental automatic from /db2backup taken at 20261027010000

Expected / interpretation: Use a timestamp proven from history and the exact target image chain; isolated destination and recovery state are part of the runbook.

Check rollforward status and recoverable time

db2 rollforward db SAMPLE query status; db2 rollforward db SAMPLE to 2026-10-27-12.00.00 using local time and stop

Expected / interpretation: Use the time zone required by the environment; do not issue STOP until status and target point are confirmed.

Recovery chain and decision flow: Select the image chain, apply logs, then validate the point

Missing logs or wrong image identity stops the flow until an alternate reachable recovery plan is selected.

Known issues, errors, fixes, and verification

Restore reaches rollforward pending but database cannot be opened.

Likely cause: Recovery logs have not been applied or the required log chain is incomplete.

Fix: Locate required logs and continue rollforward to the approved time/end; do not open at an unintended point.

Verify: Query status, complete rollforward, connect, and compare business rows to the recovery manifest.

SQL1117N indicates rollforward pending.

Likely cause: Database restore requires log application before normal access.

Fix: Run ROLLFORWARD QUERY STATUS, identify next required log and target point, then complete recovery deliberately.

Verify: Database state is normal and application acceptance query succeeds.

SQL4970N indicates point-in-time target cannot be reached.

Likely cause: Requested time precedes minimum recovery time, required log is unavailable, or time zone/chain is wrong.

Fix: Confirm minimum recovery time and timestamp convention; choose a reachable point or recover from a different valid image/log set.

Verify: Rollforward status confirms the intended reached time and reconciled transaction marker.

Hands-on lab: Recover the correct point from a mixed image set

Objective: Use a lab image inventory to recover one database and one tablespace scenario safely.

  1. Label each image with database, type, timestamp, platform, and log coverage.
  2. Draw the full/incremental/delta chain and identify the required archived logs.
  3. Perform isolated restore and query recovery status before choosing a stop point.
  4. Simulate a missing-log and wrong-target condition; stop and document recovery alternatives.
  5. Validate row counts, key transactions, objects, and application read/write access.

Answer key: The recovery manifest proves target identity, image chain, logs, reached point, and business data state. A technically successful restore is not accepted until data checks pass.

Cleanup: Keep original images and logs unchanged; remove only the disposable target database after evidence is recorded.

Review question and answer

Question: What is the minimum proof that a PIT recovery met its objective?

Answer: The correct image/log chain reached the declared timestamp, the database opened, and an application-level transaction marker confirms expected data inclusion/exclusion.
