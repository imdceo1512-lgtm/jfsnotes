Statistics, Cardinality, Parameter Markers, and Optimizer Decisions

Diagnose estimate errors, skew, and parameter-sensitive plans using targeted statistics and controlled compilation.

Level: Advanced · Effort: 2 hours
Prerequisites: C-06 and H-02.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Read table/column statistics as optimizer evidence.
  • Choose RUNSTATS options for skew and correlation.
  • Test parameter sensitivity and reoptimization deliberately.

How it works and when to use it

Optimizer estimates depend on catalog statistics such as table cardinality, column distributions, indexes, and correlation. A table-wide count can hide skew; a parameter marker can represent many selectivities but the package’s bind/reoptimization options govern when values influence plan selection. Statistics collection affects future compilation and may create plan changes. Collect enough relevant information without gathering every statistic indiscriminately.

Decision rule: Compare estimated and actual rows for the predicate; inspect table, column, distribution, and index statistics; collect targeted statistics; then re-explain and benchmark the parameter values that matter.

Worked examples and commands

Inspect column cardinality and null counts

db2 "SELECT COLNAME, COLCARD, NUMNULLS FROM SYSCAT.COLUMNS WHERE TABSCHEMA = 'APP' AND TABNAME = 'ORDERS'"

Expected / interpretation: Column statistics can be absent or stale; LASTUSED is not a substitute for freshness or distribution detail.

Refresh targeted distribution and index statistics

db2 "RUNSTATS ON TABLE APP.ORDERS ON COLUMNS (STATUS, CUSTOMER_ID) WITH DISTRIBUTION AND DETAILED INDEXES ALL"

Expected / interpretation: Choose columns from real predicates and skew; collection may be resource intensive.

Inspect high-cost package-cache entries

db2 "SELECT NUM_EXECUTIONS, TOTAL_CPU_TIME, ROWS_READ, STMT_TEXT FROM TABLE(MON_GET_PKG_CACHE_STMT(NULL, NULL, NULL, -2)) AS T ORDER BY TOTAL_CPU_TIME DESC FETCH FIRST 10 ROWS ONLY"

Expected / interpretation: Package-cache entries aggregate executions and may have been evicted; identify statement and parameterization context.

Optimizer decision flow: Statistics and parameter values drive estimates

Measure estimate error across representative parameters before deciding which statistic or compilation behavior to change.

Known issues, errors, fixes, and verification

Optimizer estimates one row but execution reads many.

Likely cause: Statistics do not describe skew/correlation or data changed substantially after collection.

Fix: Gather targeted distribution and column-group statistics where supported; validate on representative parameter values.

Verify: Re-explain, compare estimated versus observed rows, and benchmark both common and rare values.

Plan is good for one parameter and poor for another.

Likely cause: Parameter selectivity varies and the compiled section is reused under a different value distribution.

Fix: Review bind/reoptimization behavior and parameter sensitivity; test supported REOPT or statement design changes in a controlled environment.

Verify: Measure a representative parameter matrix and compare plan stability and resource cost.

RUNSTATS unexpectedly changes several workload plans.

Likely cause: A broad statistics refresh updated optimizer inputs used by other statements.

Fix: Capture important plans before maintenance, scope statistics deliberately, and use an approved regression/rollback strategy.

Verify: Compare critical statement plans and latency after the change, not just the utility return code.

Hands-on lab: Diagnose a skew-sensitive access plan

Objective: Connect one cardinality estimate mismatch to a measured parameter distribution.

  1. Select a lab query with common and rare predicate values.
  2. Compare plan estimates with measured result-row counts and package-cache metrics.
  3. Inspect catalog statistics, then collect targeted distribution statistics.
  4. Re-explain and benchmark both values under the same application compile settings.

Answer key: The diagnosis ties the estimate error to missing/stale distribution information or parameter sensitivity and shows results for both common and rare values.

Cleanup: Restore original lab statistics or data after the exercise if required.

Review question and answer

Question: Why can a plan regression follow an apparently beneficial RUNSTATS?

Answer: New statistics change optimizer estimates and can alter plans for several statements, so critical plans need post-maintenance checks.
