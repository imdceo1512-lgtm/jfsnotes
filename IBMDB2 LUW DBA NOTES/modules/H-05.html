Locks, Deadlocks, Isolation, and Transaction Design

Diagnose lock waits and deadlocks, then shorten or reorder transactions without weakening required consistency.

Level: Advanced · Effort: 2 hours
Prerequisites: C-01 and E-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Read lock owner/requester evidence.
  • Explain deadlock cycles and SQL0911N reason codes.
  • Choose transaction and isolation changes with correctness constraints.

How it works and when to use it

Locks protect concurrent changes according to isolation and access patterns. A lock wait is blocking; a deadlock is a cycle where each transaction waits on another, so Db2 selects a victim and rolls back its uncommitted work. Long units of work hold locks even while the client is idle. Lowering isolation can reduce contention but may permit data anomalies; increasing lock limits can defer rather than remove a design problem.

Decision rule: Identify owner/requester, lock object/mode, UOW age, statement, and isolation. Correct transaction duration/order or access pattern first; tune lock limits/timeouts only with a defined correctness and retry policy.

Worked examples and commands

List lock waits and owners

db2pd -db SAMPLE -locks wait

Expected / interpretation: Use with applications and transactions output to map lock IDs to application handles.

Inspect active transaction state

db2pd -db SAMPLE -transactions

Expected / interpretation: A transaction may be long because it is active, client-idle, or blocked; correlate its application and statement.

Read deadlock and lock-timeout counters

db2 "SELECT MEMBER, LOCK_WAITS, LOCK_TIMEOUTS, DEADLOCKS FROM TABLE(MON_GET_DATABASE(-2)) AS M"

Expected / interpretation: Compare interval deltas and use the lock event monitor when a historical graph is required.

Deadlock graph: Two lock orders create a cycle

Breaking consistent order or shortening the transaction removes the cycle; Db2 rolls back one victim if it occurs.

Known issues, errors, fixes, and verification

Applications receive SQL0911N with reason code 2.

Likely cause: A deadlock cycle was detected and the transaction was selected as the victim.

Fix: Review both transaction sequences and standardize lock acquisition order; make the affected unit of work safely retryable.

Verify: Repeat the concurrent lab and confirm the cycle is removed or handled within the business retry policy.

Lock timeout occurs while one application appears idle.

Likely cause: An open UOW still holds a lock while its client is idle or stalled.

Fix: Identify owner and transaction start; resolve client behavior and transaction boundaries instead of only increasing timeout.

Verify: The holder commits/rolls back promptly and subsequent requests proceed.

Changing isolation creates unexpected duplicate or missing results.

Likely cause: The application depended on stronger consistency semantics.

Fix: Document required anomalies and revalidate business invariants before isolation changes; use bounded transaction design and appropriate locking.

Verify: Concurrency tests cover expected read/write interleavings and data correctness.

Hands-on lab: Reproduce and break a deadlock cycle

Objective: Understand lock order and victim rollback in a controlled two-session lab.

  1. Create a disposable table with two rows and open two database sessions.
  2. Session A updates row 1; session B updates row 2.
  3. Session A requests row 2 while session B requests row 1; capture the deadlock and SQL0911N.
  4. Repeat with consistent row order and compare lock/event evidence.

Answer key: The deadlock is a wait-for cycle; consistent lock order or shorter transaction scope prevents the cycle and the application retries only an idempotent unit.

Cleanup: Explicitly rollback both lab sessions and drop only the disposable table.

Review question and answer

Question: Why does raising LOCKLIST not necessarily fix a deadlock?

Answer: Deadlock is a circular wait dependency; more lock memory does not break the cycle.
