Tablespace Backup and Recovery

Recover a damaged or offline tablespace while preserving whole-database consistency and object dependencies.

Level: Advanced · Effort: 3 hours
Prerequisites: F-01 and storage architecture; restore/rollforward basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Choose tablespace-level versus full-database recovery.
  • Restore and roll forward required tablespaces.
  • Identify related spaces that must share a point-in-time target.

How it works and when to use it

Tablespace recovery narrows the restored scope but does not remove consistency dependencies. A restored tablespace enters rollforward pending and needs logs. A partitioned table can span multiple spaces; point-in-time recovery of one piece requires related spaces to align. In multi-partition databases, partitions must reach a compatible point. Sometimes repairing an inaccessible container is sufficient without restore; inspect state and the underlying path before choosing media recovery.

Decision rule: Use tablespace recovery only when the failure scope, related objects, image/log set, and target point are known. Prefer full-database recovery when cross-space consistency cannot be proven.

Worked examples and commands

Restore one tablespace from a known image

db2 restore db SAMPLE tablespace (USERSPACE1) from /db2backup taken at 20261027010000

Expected / interpretation: Confirm image timestamp, target, and tablespace name. Check related objects and role/topology restrictions before execution.

Roll the restored tablespace to end-of-logs

db2 rollforward db SAMPLE to end of logs tablespace (USERSPACE1)
db2 rollforward db SAMPLE stop

Expected / interpretation: The list bounds the recovery scope. Query status before completion; related spaces may need to be included to preserve logical consistency.

Verify the recovered table-space state by member

db2 "SELECT MEMBER, TBSP_NAME, TBSP_STATE FROM TABLE(MON_GET_TABLESPACE('USERSPACE1', -2)) AS T"

Expected / interpretation: Confirm the target table space is in the expected state on every active member before resuming dependent application work.

Tablespace dependency architecture: One logical table can span multiple recovery units

Logical object consistency can cross physical tablespace boundaries.

Known issues, errors, fixes, and verification

Tablespace remains rollforward pending after restore.

Likely cause: Required archive logs have not been applied or the next log is unavailable.

Fix: Check tablespace state and rollforward status; retrieve the named log and continue. Reassess the target if the log is unavailable.

Verify: The tablespace returns to normal and representative rows/integrity/application checks pass.

A partitioned table is inconsistent after PIT recovery.

Likely cause: Related spaces containing table or index partitions were recovered to different times.

Fix: Identify all related tablespaces and recover the complete set to one approved point using the documented partition rules.

Verify: Compare recovery point for each required space and validate the full logical table.

Tablespace restore is rejected while HADR is active.

Likely cause: That tablespace operation is unsupported in the current HADR primary/standby role.

Fix: Check role/state first and follow the documented HADR recovery procedure; do not manipulate logs directly.

Verify: Both HADR state and tablespace state are healthy and shipping/replay resumes.

Hands-on lab: Recover a tablespace with a cross-space dependency

Objective: Restore a target space while keeping a multi-space table consistent.

  1. Create an isolated database with a partitioned table whose pieces use multiple tablespaces.
  2. Take a backup and make changes that affect the table.
  3. Restore the selected tablespace and inspect recovery state.
  4. Recover the required coordinated set to the same approved point and validate the whole table.

Answer key: Every related tablespace needed for logical consistency must be included at a consistent point. Physical restore of one space is not enough.

Cleanup: Drop only the disposable lab database after recording state transitions.

Review question and answer

Question: When is a single tablespace PIT recovery unsafe?

Answer: When a logical table or its dependencies span other spaces that cannot be aligned to the same recovery point.
