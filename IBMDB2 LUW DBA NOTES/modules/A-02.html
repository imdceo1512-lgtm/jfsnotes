Linux Identity, Filesystems, Permissions, and Services

Diagnose the identity and path permissions under which Db2 instance processes run.

Level: Beginner · Effort: 2 hours
Prerequisites: A-01 and basic Linux shell use.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Trace effective user and group membership.
  • Inspect every directory component on a Db2 path.
  • Check service, mount, and process limits without changing them.

How it works and when to use it

Db2 uses an instance owner identity; OS access to data, logs, diagnostics and backup paths is distinct from Db2 authority. A process needs search permission on every parent directory and suitable read/write permissions at its target. ACLs, mount flags, SELinux, service unit overrides, and `ulimit` can change effective access. Diagnose the exact service process identity rather than assuming an interactive shell matches it.

Decision rule: For path failures, inspect identity→group membership→parent traversal→target permissions→mount and service policy, in that order. Avoid broad recursive permission changes.

Worked examples and commands

Trace account and directory access

id db2inst1
namei -l /db2data/SAMPLE
getfacl -p /db2data/SAMPLE

Expected / interpretation: `namei` exposes each parent permission; `getfacl` shows ACL entries when available. Compare the service account’s groups with the path owner/group.

Inspect service and process limits

systemctl status db2.service
systemctl show db2.service -p User -p Group -p LimitNOFILE
ulimit -n

Expected / interpretation: Unit names vary by installation. `ulimit` reports the current shell, not necessarily the systemd-launched Db2 process; inspect the actual unit and process limits.

Test data-path access as the instance owner

sudo -u db2inst1 test -r /db2data; echo "read_rc=$?"; sudo -u db2inst1 test -w /db2data; echo "write_rc=$?"

Expected / interpretation: Exit code 0 means the selected access test passed. Test the actual Db2 path and owner; this does not change permissions.

Permission decision flow: Check identity and each path component before changing modes

The process must pass every layer; fixing only the leaf file cannot overcome a denied parent or mount policy.

Known issues, errors, fixes, and verification

Db2 reports permission denied although the leaf file is writable.

Likely cause: A parent directory lacks execute/search permission, ACL denies access, or the service uses another account.

Fix: Use `namei -l`, `getfacl`, and service identity to locate the exact failing component; grant the narrow required access through change control.

Verify: Run a non-destructive read/write probe as the service owner and confirm the Db2 operation succeeds.

Db2 service starts from a shell but fails after reboot.

Likely cause: The interactive shell loads `db2profile`, while the service unit lacks the expected environment, mount ordering, or resource limits.

Fix: Correct the service unit/environment and dependency ordering; do not hard-code an interactive profile into an unsafe startup hook.

Verify: Restart through systemd in a test window and verify process identity, environment, mount, and Db2 level.

A new file limit appears in a shell but not in Db2.

Likely cause: The service process inherited a different PAM/systemd limit or was not restarted after configuration change.

Fix: Update the correct service/user limit configuration, restart the service through approved procedure, and inspect `/proc/<pid>/limits`.

Verify: Confirm the running Db2 process has the intended limit and monitor file descriptor use.

Hands-on lab: Trace a failed database path access

Objective: Find the narrowest OS permission or service-context mismatch.

  1. Create a disposable nested directory owned by a lab account.
  2. Remove search permission from one parent and observe access as the instance owner.
  3. Use `namei -l`, `id`, and `getfacl` to identify the failing component.
  4. Restore the original lab permissions and verify access without recursive chmod.

Answer key: The denied parent traversal or mismatched service identity is the cause; fix only the specific owner/group/ACL entry and confirm using the same effective identity as Db2.

Cleanup: Restore the saved mode/ACL and delete only the lab path.

Review question and answer

Question: Why is `chmod -R 777` an unsafe fix for Db2 path access?

Answer: It grants unnecessary access to all users, hides the actual failed path component, and can expose database files or break required ownership controls.
