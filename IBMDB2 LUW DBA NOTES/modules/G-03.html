HADR Setup, Planned Takeover, Failover, and Reintegration

Prepare an HADR pair, prove planned role switching, and define the separate forced-failover and old-primary recovery paths.

Level: Advanced · Effort: 2.5 hours
Prerequisites: G-02 and F-05.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • List prerequisites for initial standby setup.
  • Use an unforced takeover for planned maintenance.
  • Explain forced takeover data-loss and reintegration decisions.

How it works and when to use it

HADR setup requires compatible Db2 levels/licensing, archive logging and recovery preparation, matching database identity, network service reachability, host/instance configuration, and a consistent initial backup/restore. The standby is started in standby role only after restore. Planned takeover uses the standby while primary is available and is intended to avoid data loss. Forced takeover is an outage decision that can lose shipped or replayed work; old-primary reintegration is a separate procedure.

Decision rule: Use an unforced takeover for a planned switch only after state, log currency, client routing, and rollback readiness are checked. Use forced takeover only after authorized outage declaration and explicit acceptance of possible data loss.

Worked examples and commands

Prepare a standby from a primary backup in a lab

# On primary host:
db2 backup db SAMPLE online to /db2backup include logs
# Transfer or mount the image on the standby host; use the timestamp printed by BACKUP:
db2 restore db SAMPLE from /db2backup taken at 20261027010000

Expected / interpretation: Run BACKUP on the primary, transfer or mount its image on the standby, and replace the sample timestamp with the timestamp printed by BACKUP. Complete any release-specific restore/rollforward prerequisite before starting HADR.

Start HADR in the intended roles

# On standby host:
db2 start hadr on db SAMPLE as standby
# On primary host:
db2 start hadr on db SAMPLE as primary

Expected / interpretation: Run the standby command on the standby host first, then the primary command on the primary host after HADR parameters and restore prerequisites are complete.

Perform a planned takeover from the standby

db2 takeover hadr on db SAMPLE

Expected / interpretation: Issue the unforced takeover from the standby host for a planned switch only when the pair is eligible and healthy; verify roles and client routing afterward.

Set HADR endpoints on both database copies

# On primary host:
db2 update db cfg for SAMPLE using HADR_LOCAL_HOST db2primary.example.net HADR_LOCAL_SVC 55001 HADR_REMOTE_HOST db2standby.example.net HADR_REMOTE_SVC 55001 HADR_REMOTE_INST db2inst1 HADR_TARGET_LIST db2standby.example.net:55001
# On standby host:
db2 update db cfg for SAMPLE using HADR_LOCAL_HOST db2standby.example.net HADR_LOCAL_SVC 55001 HADR_REMOTE_HOST db2primary.example.net HADR_REMOTE_SVC 55001 HADR_REMOTE_INST db2inst1 HADR_TARGET_LIST db2primary.example.net:55001

Expected / interpretation: Replace hostnames, instance, and an unused HADR port with the real topology. Confirm reciprocal DNS/address-family resolution and ensure the HADR port does not overlap the Db2 client service or another instance.

Role-switch flow: Readiness gates precede role change and service proof

Old-primary reintegration or reinitialization is a distinct step after the new primary is proven.

Known issues, errors, fixes, and verification

Standby will not start HADR because the database is not in the required state.

Likely cause: Restore was incomplete, database identity/image chain mismatches, or HADR parameters and roles are inconsistent.

Fix: Read the exact SQLCODE and diagnostics; verify restore timestamp, logs, HADR local/remote values, service resolution, and level/license.

Verify: Start standby and confirm expected role/state and log movement from both hosts.

Planned takeover is rejected.

Likely cause: Pair is not in an eligible synchronized state, replay is behind, delayed replay is configured, or version/configuration prerequisites fail.

Fix: Do not force as a workaround; resolve synchronization or schedule a different maintenance window.

Verify: Run unforced takeover in a lab and prove role reversal, client routing, and old-primary rejoin.

Old primary cannot rejoin after a forced failover.

Likely cause: The new primary has log history the old primary lacks, so reintegration is unsafe.

Fix: Follow documented reintegration only when no divergence/data loss occurred; otherwise reinitialize the old primary as a standby from the new primary.

Verify: Confirm one writable primary, standby role/state, log currency, and application writes to the new primary.

Hands-on lab: Run a controlled planned takeover

Objective: Practice the checks and validation around an unforced role switch in a paired lab.

  1. Record current roles, states, sync mode, receive/replay positions, and client endpoints.
  2. Confirm standby is synchronized and no conflicting maintenance is active.
  3. Issue unforced takeover from the standby during the approved window.
  4. Verify roles on both hosts, client reconnect, read/write behavior, and old-primary rejoin.

Answer key: The runbook separates planned takeover from forced failover and documents role, log, client, and application proof before closing the change.

Cleanup: Return the pair to the desired primary role using the documented planned procedure.

Review question and answer

Question: What is the key difference between planned takeover and forced failover?

Answer: Planned takeover requires a healthy eligible pair and is designed to preserve consistency; forced takeover can proceed after an outage with possible data loss.
