Authorities, Privileges, Roles, Groups, and Effective Access

Grant the smallest practical access set and verify effective rights across direct grants, roles, groups, and ownership.

Level: Intermediate · Effort: 2 hours
Prerequisites: D-01 and C-02.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish database authority from object privilege.
  • Use roles for repeatable job access.
  • Audit effective grants before and after a change.

How it works and when to use it

Authorities apply broadly at database or instance scope; privileges apply to specific objects. Object ownership and role/group membership also contribute to effective access. SECADM manages security objects; ACCESSCTRL grants many authorities and privileges; DBADM is broad operational authority but does not implicitly include every security administration power. Db2 role grants are active at connection establishment, while group resolution may depend on an external directory.

Decision rule: Define job roles, grant the minimum needed object privileges to those roles, grant role membership through the security administrator, and verify with catalog evidence plus an effective-access test under the target ID.

Worked examples and commands

Create a scoped reader role and grant SELECT

db2 "CREATE ROLE APP_READ"; db2 "GRANT SELECT ON TABLE APP.ORDERS TO ROLE APP_READ"; db2 "GRANT ROLE APP_READ TO USER REPORTSVC"

Expected / interpretation: Run only with the required SECADM/ACCESSCTRL/ownership authorities; role creation and grant operations are audit-sensitive.

Review direct table grants

db2 "SELECT GRANTEE, GRANTEETYPE, SELECTAUTH, CONTROLAUTH FROM SYSCAT.TABAUTH WHERE TABSCHEMA = 'APP' AND TABNAME = 'ORDERS'"

Expected / interpretation: Catalog grants are one input; include role, group, PUBLIC, schema, and ownership paths in the review.

Test least privilege as the service user

db2 "SELECT COUNT(*) FROM APP.ORDERS"

Expected / interpretation: Test with the actual application authorization ID, not a DBA session that bypasses normal rights.

Access evaluation flow: Trace the full path before changing a grant

The narrowest correct grant belongs at the specific missing authorization edge.

Known issues, errors, fixes, and verification

SQL0551N denies SELECT although the user is in a role.

Likely cause: The role membership was not granted, the connection predates the membership change, or the object/schema differs.

Fix: Check role grants and the exact object; reconnect the test session after membership changes and grant only the missing privilege to the role.

Verify: Run the operation as the target ID in a new connection and inspect the effective authorization path.

A grant succeeds but does not fix static SQL in a package.

Likely cause: Package bind-time authorization, owner privileges, or dependency invalidation differs from the dynamic test.

Fix: Inspect package owner and bind options; grant needed rights to the correct package owner/role and use the supported rebind/deployment plan.

Verify: Test the packaged application path and inspect package validity.

A broad authority was granted to solve one object failure.

Likely cause: The missing privilege was not identified and least privilege was not evaluated.

Fix: Replace broad access with an object or schema-scoped grant through a managed role; schedule revocation of temporary access.

Verify: Compare effective access and demonstrate required operation succeeds while unrelated access is denied.

Hands-on lab: Build and test a read-only role

Objective: Grant a job role access to one table and prove its boundary.

  1. Inventory existing grants for APP.ORDERS and a second unrelated table.
  2. Create a lab role and grant SELECT on only the target table.
  3. Grant the role to a test identity with security administrator approval.
  4. Connect as that identity and test allowed and denied reads.

Answer key: The intended query succeeds, unrelated table access fails, and the grant path is documented without adding DBADM or DATAACCESS.

Cleanup: Revoke the lab membership and drop the role after removing its object grants.

Review question and answer

Question: Why can cataloging direct grants alone miss effective access?

Answer: A user may inherit access through roles, groups, PUBLIC, or ownership, and package execution has additional authorization rules.
