Linux Storage, Filesystems, and I/O Diagnosis

Trace database paths to mounts/devices and separate capacity, inode, and latency incidents.

Level: Beginner · Effort: 2 hours
Prerequisites: A-01 through A-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Map a Db2 path to mount and block device.
  • Distinguish bytes, inodes, and table-space capacity.
  • Read I/O latency and queue evidence over time.

How it works and when to use it

Db2 storage has multiple layers: logical table space/container path, filesystem or raw device, volume manager/device mapping, and storage service. A filesystem may have free bytes but no inodes; a table space may reach its own maximum while the filesystem is mostly empty. Latency and queue depth are more useful than utilization alone. Identify whether data, active logs, archive logs, temporary space, and backup staging share a failure domain.

Decision rule: First resolve path identity and capacity, then collect interval latency. Do not delete Db2 files manually or grow an unrelated volume because it looks full.

Worked examples and commands

Trace filesystem and device mapping

findmnt -T /db2data
lsblk -f
df -hT /db2data
df -i /db2data

Expected / interpretation: `findmnt -T` identifies the containing mount; `df -hT` and `df -i` report byte and inode pressure separately. Verify the path is the expected volume.

Measure device latency over intervals

iostat -xz 1 5

Expected / interpretation: Compare await/latency and queue metrics across samples and with the incident baseline. Field names and units depend on sysstat version and device stack.

Inspect physical-device layout and rotational media

lsblk -o NAME,TYPE,SIZE,ROTA,MODEL,MOUNTPOINTS

Expected / interpretation: Use the device and mount mapping to connect Db2 paths with the underlying storage; RAID, SAN, and virtual layers may require platform tools.

Storage architecture: Logical Db2 storage maps through mounts to devices

Capacity and latency can fail at different layers, so preserve the entire path map.

Known issues, errors, fixes, and verification

Db2 cannot create a file although `df -h` shows free space.

Likely cause: Inodes are exhausted, quota is reached, path is read-only, or the expected mount is missing.

Fix: Check `df -i`, `findmnt`, quotas, mount flags, and exact Db2 path; restore the intended mount or quota through approved process.

Verify: Instance owner can create/remove a harmless probe file and Db2 path errors stop.

Filesystem usage is high but `du` totals do not account for it.

Likely cause: Deleted files remain open by a process, mount boundaries were skipped, or reserved space/quota is involved.

Fix: Inspect open deleted files with approved tooling and mount scope; restart only the owning process through change control.

Verify: Filesystem and process-held space return to expected levels; do not delete database files.

Disk `%util` is high and is called the root cause.

Likely cause: Utilization alone does not establish latency or saturation; device abstraction and parallel I/O matter.

Fix: Compare await, queue depth, throughput and application waits across the full stack and incident interval.

Verify: A targeted storage change improves Db2 I/O wait and representative workload latency.

Hands-on lab: Diagnose a full or slow database mount

Objective: Trace one synthetic Db2 path from directory to device and identify the correct capacity signal.

  1. Map `/db2data` using `findmnt -T` and `lsblk -f`.
  2. Compare byte, inode, and mount state outputs.
  3. Read five iostat samples and identify which fields support or weaken saturation.
  4. Write an escalation note with path, device, timestamp, and no destructive cleanup.

Answer key: State whether the failure is bytes, inodes, mount identity, or measured latency. Include the exact path and device relation; never recommend deleting database files.

Cleanup: No storage changes; use a test filesystem if simulating inode pressure.

Review question and answer

Question: Why should a DBA check both `df -h` and `df -i`?

Answer: A filesystem can have free bytes but no free inodes, preventing new files.
