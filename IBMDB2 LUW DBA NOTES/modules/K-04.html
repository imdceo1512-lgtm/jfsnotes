Enterprise DBA Capstone: Architecture, Recovery, Security, and Operations

Design and defend an evidence-based Db2 service from deployment through incident recovery and ongoing operations.

Level: Senior DBA practicum · Effort: 6 hours
Prerequisites: All modules A-01 through J-06.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Present an architecture with failure domains and operational ownership.
  • Deliver backup/HADR, security, performance, monitoring, and automation plans.
  • Complete a failure scenario and justify decisions with captured evidence.

How it works and when to use it

The capstone scenario is a transactional Db2 LUW service with a Linux primary site, a remote HADR standby, nightly backup window, sensitive customer data, mixed OLTP/reporting workload, and strict RPO/RTO. The design must specify supported topology/version, host/storage/network dependencies, schemas and authorities, service-level targets, backup/log retention, HADR mode, monitoring dimensions, capacity headroom, and automation controls. A complete design includes operating procedures and evidence—not only a component diagram.

Decision rule: Design from business objectives and threat/failure domains, prove each operational path with a lab, and record assumptions. Senior review asks whether the design prevents a single missing dependency from invalidating recovery, access control, or failover.

Worked examples and commands

Establish service and Db2 baseline

db2level; db2 get instance; db2 get db cfg for SAMPLE show detail

Expected / interpretation: Record version, topology, effective config, and target identity for the architecture pack.

Validate workload and performance evidence

db2 "SELECT MEMBER, TOTAL_CPU_TIME, ROWS_READ, ROWS_RETURNED FROM TABLE(MON_GET_DATABASE(-2)) AS M"; db2pd -db SAMPLE -activestatements

Expected / interpretation: Use timed deltas and representative queries; state units, interval, and service objective.

Review access and recovery evidence

db2 "SELECT GRANTEE, GRANTEETYPE FROM SYSCAT.TABAUTH WHERE TABSCHEMA = 'APP'"; db2 list history backup all for SAMPLE; db2pd -db SAMPLE -hadr

Expected / interpretation: Privileges, backup history, and HADR state are separate evidence sources; each needs an effective-access, restore, or failover rehearsal.

Enterprise service architecture: One service depends on multiple independently tested paths

Monitoring, automation, capacity, security ownership, and application acceptance span every layer and must be tested end to end.

Known issues, errors, fixes, and verification

Architecture has HADR but no usable restore path.

Likely cause: Replication is treated as backup and no independent image/log chain or key retrieval path is rehearsed.

Fix: Add isolated backup retention and full recovery drill with keys, access, target capacity, and application validation.

Verify: Restore before a synthetic bad transaction and meet measured RPO/RTO.

Security matrix gives every DBA DBADM and DATAACCESS.

Likely cause: Operational job duties and security administration were not separated.

Fix: Use roles for job functions, distinguish SECADM/ACCESSCTRL/DBADM/SYSMON needs, and test deny boundaries.

Verify: Each role passes required tasks and is denied unrelated access.

Capstone runbook closes on a green Db2 command while service is still failing.

Likely cause: Database health was not tied to client connectivity, application behavior, latency, or data correctness.

Fix: Add end-to-end acceptance queries, service latency, client routing, and owner sign-off.

Verify: Synthetic user transaction succeeds through the application path and agreed SLO returns to normal.

Hands-on lab: Enterprise Db2 design and incident defense

Objective: Deliver an architecture and runbook, then defend it under a simulated site outage and performance incident.

  1. Draw primary, HADR, backup, client, identity, network, storage, and operator-access failure domains.
  2. Define RPO/RTO, full/incremental/log backup chain, HADR mode, retention, and measured drill calendar.
  3. Build role matrix, TLS/key lifecycle, workload baseline, capacity forecast, and alert thresholds.
  4. Present a runbook for site failure and validate primary isolation, standby currency, takeover decision, client reconnection, and business data.
  5. Run a performance regression case; correlate EXPLAIN, activity, host I/O, and measured service response.
  6. Submit sanitized evidence, assumptions, rollback limits, and unresolved risk owners.

Answer key: Passing design includes a distinct backup path, tested failover and restore, least-privilege roles, measurable workload baselines, failure-aware automation, and an application-level acceptance test. Every major claim is backed by a command result, rehearsal, or explicit unresolved assumption.

Cleanup: All practice uses synthetic data and isolated targets; remove lab users, roles, databases, and generated files under the lab cleanup plan.

Review question and answer

Question: What distinguishes an operational architecture from a product diagram?

Answer: It identifies failure domains, owners, exact recovery decisions, prerequisites, capacity, client paths, and evidence that proves the service is restored.
