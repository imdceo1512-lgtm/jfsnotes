Client Catalogs, Drivers, Aliases, and Remote Connections

Build and test a remote connection path from client catalog entries through DNS and service port to the database.

Level: Intermediate · Effort: 2 hours
Prerequisites: A-05 and B-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Explain node and database directory entries.
  • Catalog a remote TCP/IP database alias.
  • Test with the same driver and transport path as the application.

How it works and when to use it

A remote CLP alias resolves through the local node directory to a host and service, then through the database directory to a database name. CLI/ODBC/JDBC clients may instead use a DSN or driver configuration. Catalog entries can be stale or point to the wrong endpoint. A successful TCP connection does not prove database authentication or database availability.

Decision rule: Inspect local directory state, resolve host and port, verify transport reachability, then connect through the production driver and record CURRENT SERVER and CURRENT USER. Do not fix network failures by changing database privileges.

Worked examples and commands

Catalog a TCP/IP node

db2 catalog tcpip node LABNODE remote db2lab.example.net server 50000

Expected / interpretation: Use approved host and service values; DNS alias and numeric port should match the server configuration.

Catalog a database alias and connect

db2 catalog database SAMPLE as LABSAMPLE at node LABNODE authentication server; db2 connect to LABSAMPLE

Expected / interpretation: Use the server database name and authentication method supported by the deployment.

Inspect catalog entries

db2 list node directory; db2 list database directory

Expected / interpretation: Directory output is client-local. Confirm which client install and user profile the application actually loads.

Connection path architecture: Client alias resolution precedes server authentication

Test each layer in order and preserve the client context used by the real application.

Known issues, errors, fixes, and verification

SQL1013N says the alias cannot be found.

Likely cause: The database alias is absent from this client directory or the application uses another client profile.

Fix: Catalog the database alias in the client context used by the process or configure the supported DSN entry.

Verify: List the database directory as the same OS user and reconnect with the exact alias.

SQL30081N reports a TCP/IP connection failure.

Likely cause: Wrong DNS result, port/service mismatch, route/firewall block, listener down, or TLS protocol mismatch.

Fix: Test each network hop and compare with server SVCENAME/SSL_SVCENAME and DB2COMM; correct the first failing layer.

Verify: Connect from the application host through the configured driver and inspect server-side connection evidence.

CLP connects but JDBC/ODBC application does not.

Likely cause: Different driver level, DSN, TLS options, credentials, or client configuration file.

Fix: Capture application driver version and effective DSN properties; test that exact driver and alias rather than copying the CLP result.

Verify: Execute a harmless identity query through the application’s driver and compare server, user, and TLS state.

Hands-on lab: Build a disposable remote alias

Objective: Trace catalog resolution and test a remote connection without production changes.

  1. Use a lab client profile and approved test endpoint.
  2. Catalog a named TCP/IP node and database alias.
  3. List both directories and verify host, service, alias, and authentication method.
  4. Connect and query CURRENT SERVER and CURRENT USER.

Answer key: The alias resolves through the expected node entry and test connection reaches the intended server/database using the expected identity.

Cleanup: Uncatalog only LABSAMPLE and LABNODE from the disposable client profile.

Review question and answer

Question: What does a successful port probe prove?

Answer: Only that a network path reached a listener; it does not prove the alias, TLS negotiation, authentication, database existence, or authorization.
