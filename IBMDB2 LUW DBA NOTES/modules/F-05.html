Full Restore and Redirected Restore

Restore a selected full image to a controlled target and relocate containers when the original paths are unavailable.

Level: Advanced · Effort: 3 hours
Prerequisites: F-01 through F-04; isolated target instance and storage.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Select a full image and target database deliberately.
  • Perform redirected restore with reviewed container mapping.
  • Recognize when the restored database still needs rollforward recovery.

How it works and when to use it

RESTORE recreates the state captured in an image. Restoring into an existing database obtains an exclusive connection and replaces its contents; restoring into a new database requires instance attachment and creation authority. A redirected restore changes container/storage paths through a multi-step process. Review the generated client-side script before running it. If the image was taken with rollforward recovery enabled, restore can leave the database pending until required logs are applied.

Decision rule: Before restore, confirm source alias, image timestamp, target alias, overwrite intent, platform compatibility, storage map, log paths, required keys, and rollforward expectation.

Worked examples and commands

Restore a full image into a new lab alias

db2 restore db SAMPLE from /db2backup taken at 20261027010000 into SAMPLE_TEST

Expected / interpretation: Use an exact image timestamp and a non-existing target alias. Check code page, territory, space, log paths, release compatibility, and package/routine implications before application testing.

Generate and review a redirected restore script

db2 restore db SAMPLE from /db2backup taken at 20261027010000 redirect generate script SAMPLE_restore.clp
# Review every target path and restore option in SAMPLE_restore.clp before execution
db2 -tvf SAMPLE_restore.clp

Expected / interpretation: IBM documents generation, review/editing, and execution as separate steps. The script can contain destructive restore clauses, so inspect the target and all paths first.

Check whether the restored database needs rollforward

db2 rollforward db SAMPLE_TEST query status

Expected / interpretation: Use the restored alias and actual rollforward status to choose the next recovery step; do not open it for application work until recovery is complete.

Redirected restore flow: Restore to new storage with reviewed container mapping

The target layout is an explicit recovery input; copying data is only one stage of making the database usable.

Known issues, errors, fixes, and verification

Restore reports a path/container error or cannot allocate target storage.

Likely cause: Target filesystem is absent/full, inaccessible to the instance owner, or incompatible with the saved container map.

Fix: Check mount, ownership, capacity, container type, and storage-group mapping; regenerate or correct the redirect script from the verified image.

Verify: Inspect final container map and tablespace state; compare free capacity with target size.

Restore overwrites an unexpected database.

Likely cause: The operator misread INTO/REPLACE semantics and targeted an existing alias.

Fix: Stop before execution; choose an isolated target alias and review every destructive clause in the command and generated script.

Verify: Print target alias and image timestamp in the precheck; verify database identity and expected contents after restore.

A restored database returns `SQL1117N` on connection.

Likely cause: The database is rollforward pending and still needs log application.

Fix: Query recovery status and locate the required log chain; follow the approved end-of-logs or point-in-time procedure.

Verify: Rollforward status completes, connection succeeds, and application checks pass.

Hands-on lab: Redirect a restore into alternate storage

Objective: Recover a synthetic image into new storage without changing its source.

  1. Create a disposable target and verify destination mounts/free space.
  2. Generate a redirected restore script for a known image.
  3. Review alias, containers, storage groups, and log paths; mark destructive clauses.
  4. Run the script in the lab, then inspect containers, tablespace state, rollforward status, and a known row count.

Answer key: Use a non-production target, exact timestamp, reviewed paths, and explicit restore completion. If rollforward is pending, the database is not yet ready for normal application use.

Cleanup: Drop only the disposable lab target; retain source backup images.

Review question and answer

Question: Why does successful RESTORE not always mean the database is ready for applications?

Answer: A recoverable image can leave the database rollforward pending; logs and post-restore checks are still required.
