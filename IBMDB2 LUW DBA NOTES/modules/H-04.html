Index and Query Design

Design indexes from filtering, joining, ordering, and write workload evidence, then measure their read and write costs.

Level: Advanced · Effort: 2 hours
Prerequisites: C-02 and H-02/H-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Order compound keys from workload predicates and selectivity.
  • Evaluate covering and clustering needs against write overhead.
  • Use advisor output as a candidate, not an automatic change.

How it works and when to use it

A B-tree index can reduce data-page reads or satisfy order, but every insert/update/delete can incur index maintenance and consume storage. Key order affects usable prefixes and selectivity; a plausible index may add little if the query is non-sargable or statistics mislead the optimizer. Db2 Design Advisor recommendations are workload-specific and may include changes beyond indexes.

Decision rule: Start with captured SQL and access plan, determine predicate/join/order needs and existing indexes, model selectivity and write frequency, then test one candidate on representative data. Review DDL and storage/maintenance impact before deployment.

Worked examples and commands

Inspect existing index key definitions

db2 "SELECT INDNAME, UNIQUERULE, COLNAMES, CLUSTERING FROM SYSCAT.INDEXES WHERE TABSCHEMA = 'APP' AND TABNAME = 'ORDERS'"

Expected / interpretation: Catalog field support and key representation are release-specific; verify against SYSCAT.INDEXES on the target.

Ask Design Advisor for candidates

db2advis -d SAMPLE -s "SELECT ORDER_ID FROM APP.ORDERS WHERE CUSTOMER_ID = 10042 AND STATUS = 'PENDING'"

Expected / interpretation: Read-only workload analysis still uses explain tables and may create advisor data; inspect generated recommendations and disk assumptions.

Test a reviewed lab index

db2 "CREATE INDEX APP.IX_ORDERS_CUST_STATUS ON APP.ORDERS (CUSTOMER_ID, STATUS)"

Expected / interpretation: Create only in a disposable lab or after change review; measure matching query and write path before rollout.

Index design flow: Index structure follows workload evidence

Optimize the workload as a whole, not one isolated SELECT.

Known issues, errors, fixes, and verification

An index is not used despite matching a column name.

Likely cause: Predicate order/type, function wrapping, cast, selectivity, statistics, or optimizer cost prevents a useful index access.

Fix: Inspect predicate and plan, align data types and expression design, refresh relevant statistics, and test actual predicate values.

Verify: Explain shows the intended index access and measured reads/latency improve for the workload.

Read query improves but write latency or storage worsens.

Likely cause: New index maintenance cost affects high-volume DML and index pages consume additional storage.

Fix: Measure read benefit against write overhead, size, logging, backup, and reorganization costs; drop only after an approved rollback plan.

Verify: Test representative mixed read/write workload and monitor index usage over a full business cycle.

Advisor recommends too many objects.

Likely cause: Input workload frequency, statement mix, disk limit, or explain/statistics context does not represent production.

Fix: Curate representative SQL, assign realistic frequency, set a practical disk limit, and compare candidates incrementally.

Verify: Only candidates with measured net benefit survive workload testing and impact review.

Hands-on lab: Evaluate a compound index candidate

Objective: Use a real predicate, current index inventory, and cost evidence to select or reject a candidate.

  1. Capture representative SELECT and DML workload for the lab table.
  2. Inspect plan predicates and current key order.
  3. Run db2advis on a representative statement or workload file.
  4. Test one candidate index and compare reads, latency, storage, and write throughput.

Answer key: The decision accounts for usable key prefix, selectivity, ordering, write frequency, and measured total workload cost.

Cleanup: Drop only the lab index after restoring original plan conditions.

Review question and answer

Question: Why can a covering index still be a bad production choice?

Answer: It may reduce a read while increasing write cost, storage, logging, backup size, and maintenance across the full workload.
