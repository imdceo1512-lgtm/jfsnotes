Fleet Automation and Runbook Integration

Coordinate multi-instance operations with inventory, concurrency limits, canaries, independent status, and ticket evidence.

Level: Advanced · Effort: 2 hours
Prerequisites: J-04/J-05 and B-06.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Use inventory labels instead of broad shell globs.
  • Limit concurrency and stop on per-host failure.
  • Attach safe evidence and ownership to an operational runbook.

How it works and when to use it

Fleet work multiplies small mistakes across hosts and instances. Inventory must identify platform, instance owner, installation copy, topology, maintenance class, and criticality. A canary catches assumptions before broad rollout; rate limits protect shared infrastructure. Each target needs an independent status and rollback decision. Ticket/runbook integration should publish action, owner, time, result, and sanitized evidence, never secrets or unreviewed destructive commands.

Decision rule: Start with read-only inventory collection, select one canary, cap parallel work, require health gates between batches, and retain a per-target result including skipped/failed/unknown states.

Worked examples and commands

Run read-only level check against an allowlisted host list

while IFS= read -r host; do [[ -z "$host" || "$host" == \#* ]] && continue; ssh -o BatchMode=yes -o ConnectTimeout=5 "$host" "sudo -iu db2inst1 /home/db2inst1/sqllib/bin/db2level" || printf "FAILED	%s
" "$host"; done < hosts.txt

Expected / interpretation: Use a reviewed inventory and approved privilege path; keep this serial example rate-limited and read-only.

Inspect a single target before a fleet batch

ssh db2lab01 "sudo -iu db2inst1 /home/db2inst1/sqllib/bin/db2 get instance"

Expected / interpretation: Verify host mapping, profile, and target identity at canary before increasing scope.

Summarize per-target result rows

awk -F "	" "{status[\$1]++} END {for (s in status) print s,status[s]}" fleet_status.tsv

Expected / interpretation: Keep status values explicit: SUCCESS, FAILED, SKIPPED, and UNKNOWN; do not collapse partial fleet success.

Fleet rollout architecture: Canary and health gates limit the blast radius

Stop rollout on a failing gate and preserve each host’s actual state.

Known issues, errors, fixes, and verification

Fleet job changes an unintended host or instance.

Likely cause: Inventory wildcard, alias, or environment mapping was broader than the reviewed target set.

Fix: Use versioned explicit inventory, validate target labels, print planned scope, and require canary approval.

Verify: Compare planned and actual host/instance IDs in the per-target manifest.

Many hosts fail simultaneously during an automated rollout.

Likely cause: Concurrency exceeds shared network, storage, or management-plane capacity.

Fix: Set a low concurrency limit, batch by failure domain, and add health gates and pause conditions.

Verify: Load-test the orchestration in staging and verify automatic pause on threshold breach.

Ticket is marked complete despite partial failures.

Likely cause: Orchestration reports aggregate process exit but not per-target state.

Fix: Publish one status per target and require zero FAILED/UNKNOWN or explicit owner disposition before closure.

Verify: Inject one canary failure and ensure the runbook remains open with exact failed targets.

Hands-on lab: Build a canary-first fleet operation

Objective: Plan a read-only inventory sweep and controlled deployment gate.

  1. Define explicit hosts, instances, topology, owners, and exclusions.
  2. Collect Db2 levels serially from one canary and validate identity.
  3. Define batch size, pause thresholds, and per-target status model.
  4. Publish sanitized results and require human disposition for failed/unknown targets.

Answer key: The execution manifest exactly matches inventory, canary success precedes rollout, and ticket closure requires explicit per-target outcomes.

Cleanup: Remove lab host inventory and synthetic status file.

Review question and answer

Question: Why is aggregate success insufficient for fleet operations?

Answer: Some targets may have failed, been skipped, or ended in unknown state; each instance needs an independently verified result.
