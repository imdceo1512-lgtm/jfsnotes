Performance Method: Baseline, Workload, and Bottleneck Isolation

Use repeatable workload evidence to distinguish database, host, storage, concurrency, and client bottlenecks.

Level: Advanced · Effort: 2 hours
Prerequisites: E-03 through E-06.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Define the regression and comparison baseline.
  • Normalize throughput, latency, concurrency, and data volume.
  • Test one bottleneck hypothesis at a time.

How it works and when to use it

Performance is an end-to-end property of the application request, Db2 work, host resources, storage, and network. A change in throughput can alter latency even when query plans remain stable. Compare like workload, parameter values, concurrency, data volume, member placement, and cache state. Capture before/after measurements with uncertainty and rollback criteria. A single elapsed-time sample is weak evidence.

Decision rule: First determine which user-visible metric regressed, then correlate it to workload and resource evidence. Change one variable at a time, repeat enough trials to see normal variance, and keep a rollback threshold.

Worked examples and commands

Capture active SQL during a regression

db2pd -db SAMPLE -activestatements

Expected / interpretation: Snapshot active work with timestamp/member; short statements may finish before inspection.

Read database workload counters

db2 "SELECT MEMBER, TOTAL_CPU_TIME, ROWS_READ, ROWS_RETURNED, LOCK_WAITS, DEADLOCKS FROM TABLE(MON_GET_DATABASE(-2)) AS M"

Expected / interpretation: Treat counters as cumulative; take interval deltas and identify member scope.

Collect host resource samples

vmstat 1 10; iostat -xz 1 10

Expected / interpretation: Use matched time windows and map devices to Db2 paths; baseline values vary by platform and workload.

Performance analysis flow: Start from user impact and isolate the first constrained layer

A valid tuning conclusion explains both request-level impact and the resource that constrained it.

Known issues, errors, fixes, and verification

A tuning change appears faster in one run and slower in the next.

Likely cause: Cache state, concurrency, parameter distribution, background work, or host contention differs across runs.

Fix: Control workload variables, warm/cold state, concurrency, and test interval; repeat and compare distributions rather than one run.

Verify: The result is repeatable across comparable trials and exceeds normal baseline variance.

CPU is high but the affected request is waiting on storage or locks.

Likely cause: Host-wide utilization was used without query wait and application-level evidence.

Fix: Correlate statement activity, lock waits, buffer-pool physical reads, device latency, and service response time in the same interval.

Verify: The chosen metric changes when the tested bottleneck is relieved.

A database parameter is changed during diagnosis and the cause becomes unclear.

Likely cause: Multiple variables changed before a baseline and rollback point were recorded.

Fix: Restore a known configuration or capture exact effective values; change only one parameter with explicit expected effect.

Verify: The result can be attributed to one change and reversed if the acceptance test fails.

Hands-on lab: Establish a before-and-after performance baseline

Objective: Produce a reproducible test that separates latency, throughput, and resource cost.

  1. Define the affected transaction, user-visible latency percentile, and throughput.
  2. Capture Db2 counters and host resource metrics over aligned intervals.
  3. Record SQL text/parameters, concurrency, data volume, cache state, and member.
  4. Apply one lab change, repeat identical trials, and compare distributions.

Answer key: The report includes workload identity, measurement interval, throughput and latency, Db2/host metrics, normal variance, and a pass/rollback threshold.

Cleanup: Revert the lab-only change and stop benchmark workload.

Review question and answer

Question: Why does a single faster execution not prove a performance improvement?

Answer: It may reflect cache, concurrency, or workload differences; repeat controlled trials and compare representative measurements.
