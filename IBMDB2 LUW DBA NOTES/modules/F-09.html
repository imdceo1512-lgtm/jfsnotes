Recovery Failure Drills and Runbooks

Use state, image, log, and data evidence to resolve recovery faults without improvising destructive commands.

Level: Advanced · Effort: 4 hours
Prerequisites: All Phase F lessons and an isolated recovery lab.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Classify recovery state before issuing a repair.
  • Select safe responses to missing logs, broken chains, and wrong targets.
  • Produce a runbook with explicit stop gates and post-recovery data checks.

How it works and when to use it

Freeze evidence first: target identity, source image and timestamp, database/tablespace states, last successful log, next required log, archive path, and exact command output. Do not delete or rename logs to make a sequence fit. Restore pending, rollforward pending, rollforward in progress, and normal state allow different next steps. A failed incremental restore may require a documented ABORT; a recovery command may need a state-specific retry.

Decision rule: Do not issue STOP, CANCEL, ABORT, REPLACE, or another RESTORE until current state and approved data-loss boundary are recorded. Escalate if the required chain or target cannot be proven.

Worked examples and commands

Capture recovery state before action

db2 rollforward db SAMPLE query status
db2 get db cfg for SAMPLE show detail

Expected / interpretation: Record next required log and effective archive/retrieval configuration with instance/database identity and timestamp.

Apply a verified log chain and complete

db2 rollforward db SAMPLE to end of logs
db2 rollforward db SAMPLE stop
db2 connect to SAMPLE

Expected / interpretation: Use only when end-of-logs is approved and required logs are accessible. A successful connection is not complete application acceptance.

Capture log-chain and archive state during a drill

db2pd -db SAMPLE -logs

Expected / interpretation: Record current log number, archive status, and chain context with the recovery timeline before changing configuration or retrying recovery.

Recovery incident decision flow: State first, evidence second, then controlled action

This sequence prevents accidental data loss from premature STOP/CANCEL or restoring the wrong target.

Known issues, errors, fixes, and verification

The next log named by rollforward is unavailable.

Likely cause: Archive retrieval failed, retention removed a needed log, or the path contains another database’s log chain.

Fix: Locate the exact log from the approved archive, verify database identity/sequence and permissions, and use the supported overflow/retrieval path.

Verify: Rollforward passes the missing sequence; transaction markers match the approved target.

`SQL4970N` leaves the database pending after PIT attempt.

Likely cause: The chosen timestamp cannot be established from available log evidence.

Fix: Reconcile image completion, available logs, timezone, and business boundary; choose a supported point with recovery-owner approval.

Verify: Repeat the proposed target in a clean lab and prove transaction visibility around the target.

A retry produces a different pending state.

Likely cause: A prior utility remains in progress, an incremental restore was not aborted cleanly, or database and tablespace operations were mixed.

Fix: Capture status and utility output; follow the documented ABORT/CANCEL/restart procedure for that exact state.

Verify: State query matches the expected next step and the rehearsed sequence completes from a clean target.

Hands-on lab: Run a fault-injected recovery tabletop

Objective: Resolve synthetic chain, log, and timestamp failures with explicit go/no-go gates.

  1. Review a packet with a missing delta image, a missing log, and a PIT timestamp in a different timezone.
  2. Classify current state and list the evidence needed before another command.
  3. Restore missing artifacts in an isolated target and execute recovery.
  4. Run database and application checks; write a timeline and decision record.

Answer key: Establish identity/state, reconstruct exact image and log chain, convert timestamp unambiguously, recover, then validate technical and business outcomes. Any unproven target is a no-go.

Cleanup: Preserve synthetic evidence; destroy only the isolated target after review.

Review question and answer

Question: What should happen before a state-changing recovery command after an unexpected message?

Answer: Capture QUERY STATUS, configuration, utility output, and target identity, then follow the documented procedure for the observed state.
