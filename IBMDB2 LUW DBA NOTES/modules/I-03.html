Db2 Upgrade Planning and Execution

Prepare and upgrade a supported Db2 instance/database with precheck, compatibility, HADR, and post-upgrade gates.

Level: Advanced · Effort: 2 hours
Prerequisites: I-02, F-02, G-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Run the target-level readiness check.
  • Separate installation, instance upgrade, and database upgrade.
  • Validate applications, packages, backup baseline, and new recovery path.

How it works and when to use it

A server upgrade has stages: install target copy, check database/instance readiness with target-level utilities, upgrade the instance as root/administrator, upgrade each database as SYSADM, then validate packages, objects, application connections, and backup/recovery. The database upgrade cannot be reversed in place. HADR upgrade requirements depend on source level and topology; standby log positions and role handling must follow the version-specific procedure.

Decision rule: Use the target release’s db2ckupgrade from its install image, fix every error and review warnings, preserve a tested backup, upgrade through the supported path, then take the required new full backup and run business checks.

Worked examples and commands

Run target-version readiness check

/opt/ibm/db2/V12.1/bin/db2ckupgrade SAMPLE -l /secure/upgrade-precheck.log

Expected / interpretation: Run from the target copy utilities as instance owner/SYSADM per platform instructions; log file is an operator artifact, not course content.

Upgrade the instance on Linux/UNIX

/opt/ibm/db2/V12.1/instance/db2iupgrade db2inst1

Expected / interpretation: Run as root from target copy after prechecks and stop; exact fenced user option may be needed.

Upgrade a cataloged database

db2 upgrade database SAMPLE

Expected / interpretation: Run as the instance owner with SYSADM after instance upgrade; this is forward-only, so use an isolated rehearsal.

Upgrade sequence: Readiness and backup gates precede forward-only changes

Do not mark complete until the target-level database and service pass their acceptance tests.

Known issues, errors, fixes, and verification

db2ckupgrade returns DBI1205E or identifies incompatible objects.

Likely cause: Readiness check found unsupported values, object names, package/feature conditions, or HADR log-position mismatch.

Fix: Resolve each reported condition using target-release guidance and rerun the target-level check; do not skip the gate.

Verify: Precheck reports database can be upgraded and required version banner is from the intended target copy.

UPGRADE DATABASE fails with SQL1704N reason code 3.

Likely cause: Upgrade log space is insufficient or upgrade hit a database-specific prerequisite.

Fix: Follow the documented failure response, terminate the CLP if required, correct log capacity, and rerun only after confirming current upgrade state.

Verify: Check upgrade completion and database diagnostics, then run catalog/object validation.

Applications fail after database upgrade.

Likely cause: Invalid packages, removed behavior, driver mismatch, authorization change, or application SQL incompatibility.

Fix: Use invalid-object/package inventory, supported REBIND and application deployment procedures, and target-level drivers.

Verify: Run application smoke tests for critical SQL and capture package validity and error rates.

Hands-on lab: Build a Db2 version-upgrade rehearsal

Objective: Practice staged gates using a clone and target-level utilities.

  1. Inventory source/target versions, topology, HADR, add-ons, applications, and clients.
  2. Run target-level db2ckupgrade and resolve warnings/errors.
  3. Rehearse instance and database upgrade on a restored clone.
  4. Validate packages, authentication, client drivers, workload, and a new full backup.

Answer key: The rehearsal documents every stage, forward-only point, outage estimate, recovery strategy, and application acceptance result.

Cleanup: Use only clone data; retain the rehearsal’s upgrade notes outside the release course.

Review question and answer

Question: Why should db2ckupgrade run before instance upgrade?

Answer: It checks database and instance readiness using target-version logic before the source environment is moved to the new code level.
