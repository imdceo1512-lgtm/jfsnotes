HA/DR Architecture and Failure Domains

Choose complementary availability controls by mapping failures to service impact, RPO, and RTO.

Level: Advanced · Effort: 2.5 hours
Prerequisites: F-02 and B-06.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Map host, site, storage, network, and operator failure domains.
  • Explain what backup, HADR, and cluster automation each protect.
  • Design recovery paths that do not share the primary failure domain.

How it works and when to use it

High availability reduces service interruption for selected component failures. Disaster recovery restores service after wider site or administrative failure. HADR streams logs to a standby; backup and archived logs provide a separate recovery path; cluster automation may detect failures and orchestrate resource movement but does not replace data protection. Shared storage, identity, DNS, certificates, and operator access can create correlated failure paths.

Decision rule: Start with service dependencies and failure scope, then choose local cluster HA, HADR, backup recovery, or combinations. Validate each path with a timed drill and test that management/control dependencies survive the same incident.

Worked examples and commands

Inventory database and host dependencies

db2 get db cfg for SAMPLE; db2 list history backup all for SAMPLE

Expected / interpretation: Configuration and history are design inputs; confirm restore evidence separately.

Map service-critical host paths

hostname -f; df -h /db2data /db2logs /db2backup

Expected / interpretation: Document whether storage, network, and credentials share the same site or control plane.

Check HADR roles when configured

db2pd -db SAMPLE -hadr

Expected / interpretation: An HADR status snapshot demonstrates current pairing only, not failover readiness.

Availability architecture: Protect the service across distinct failure domains

Use complementary controls and test each path against the failure it is meant to survive.

Known issues, errors, fixes, and verification

A standby is assumed to protect against ransomware or operator error.

Likely cause: Replication can replay destructive logical changes to the standby.

Fix: Retain isolated immutable backups and rehearsed point-in-time recovery in addition to replication.

Verify: Demonstrate restoration to a clean isolated target from before a synthetic bad change.

HA design depends on a shared DNS or storage service that fails with the primary site.

Likely cause: Dependency failure domains were not mapped end to end.

Fix: Identify and diversify critical DNS, identity, key, network, storage, and operator-access dependencies.

Verify: Exercise a site-loss scenario and prove clients and operators can reach the recovery environment.

RPO/RTO is asserted from product architecture alone.

Likely cause: No measured failure drill covers detection, decision, role change, client redirection, validation, and workload restart.

Fix: Run an approved timed drill with explicit data-loss and service acceptance criteria.

Verify: Record actual recovery point and restoration duration against service objectives.

Hands-on lab: Draw a failure-domain design

Objective: Show which control addresses each failure and where shared dependencies remain.

  1. List service dependencies and classify host, rack, site, storage, identity, network, and operator failures.
  2. Map each failure to HADR, cluster, backup, or manual recovery control.
  3. Mark shared dependencies and required secrets/keys.
  4. Define a measurable drill for each critical failure scenario.

Answer key: Each scenario has an owner, recovery path, data-loss bound, time target, and proof criteria; backups remain independent of replicated changes.

Cleanup: Architecture exercise only.

Review question and answer

Question: Why do HADR and backup solve different recovery problems?

Answer: HADR maintains a log-replayed standby for availability; an independent backup/log chain can recover from logical corruption or historical points that replication may reproduce.
