db2pd, Snapshots, and Monitor Table Functions

Choose current-state tools and monitor functions for application, workload, database, and utility questions.

Level: Intermediate · Effort: 1.5 hours
Prerequisites: B-01, C-03, and E-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Select db2pd options for fast current-state evidence.
  • Use monitor functions for scoped SQL metrics.
  • Calculate rates from repeated timestamped counters.

How it works and when to use it

db2pd reads engine memory and can provide fast operational details without requiring a database connection for many options. Database-scoped options need an active database and suitable authority. MON_GET routines expose relational metrics and member scope; many counters accumulate over an interval. Older snapshot interfaces are deprecated for some use cases. A snapshot is a point-in-time observation, not a trend or causal explanation.

Decision rule: Use db2pd to answer immediate engine-state questions, monitor functions for structured metrics and analysis, and repeated samples for rates; include member and scope in every aggregate.

Worked examples and commands

List database applications quickly

db2pd -db SAMPLE -applications

Expected / interpretation: Requires appropriate monitoring authority; interpret app handles and member columns in the correct instance.

Query live database counters

db2 "SELECT MEMBER, TOTAL_CPU_TIME, ROWS_READ, ROWS_RETURNED FROM TABLE(MON_GET_DATABASE(-2)) AS M"

Expected / interpretation: Counters are cumulative within their scope. Preserve two samples and elapsed time to derive workload rates.

Inspect currently active SQL statements

db2pd -db SAMPLE -activestatements

Expected / interpretation: The option shows current activity; a short query may finish before collection, so pair with event evidence for history.

Monitoring data flow: Current state and trend answer different questions

Use one-shot state for triage and deltas for trends; correlate both with workload and time.

Known issues, errors, fixes, and verification

db2pd returns no database details.

Likely cause: Database is inactive, wrong instance environment, wrong database name, or authority is insufficient.

Fix: Verify instance identity and active database state; use the minimum monitor authority and correct database scope.

Verify: Run db2pd at host and confirm output identifies the expected database/member.

Two member counters are summed into a misleading value.

Likely cause: The query aggregated partition/member scoped counters without considering coordinator or duplicate scope.

Fix: Keep MEMBER in the output and apply aggregation only where the metric definition supports it.

Verify: Compare per-member deltas with a supported database-wide view and known workload volume.

Deprecated snapshot output is used for a new monitoring design.

Likely cause: A legacy script was copied without checking current supported interfaces.

Fix: Migrate the query to the supported MON_GET function and preserve the old baseline definition for comparison.

Verify: Run both read-only queries side by side during migration and reconcile units and scope.

Hands-on lab: Calculate a counter rate safely

Objective: Measure database work across a bounded interval.

  1. Capture MON_GET_DATABASE counters and UTC time at T0.
  2. Wait a known interval while a stable lab workload runs.
  3. Capture the same counters at T1 and retain member identifiers.
  4. Calculate delta divided by elapsed seconds and explain units.

Answer key: The report shows raw counters, elapsed interval, member scope, delta, and derived per-second rate; one snapshot is never labeled a rate.

Cleanup: Stop only the synthetic lab workload.

Review question and answer

Question: What evidence turns a monitor counter into a rate?

Answer: Two comparable samples with known elapsed time and preserved member/database scope.
