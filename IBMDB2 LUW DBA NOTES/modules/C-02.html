Schemas, Tables, Indexes, Constraints, and Dependencies

Create and inspect Db2 objects while preserving keys, dependency order, and application contracts.

Level: Intermediate · Effort: 2 hours
Prerequisites: C-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Create a table with keys and constraints.
  • Inspect indexes and dependencies before DDL.
  • Plan object changes in dependency order.

How it works and when to use it

Schemas group names; tables own data; indexes provide access paths; constraints enforce data rules; views, packages, triggers, and routines may depend on those objects. DDL can invalidate or block dependent application objects and may commit implicitly. Catalog metadata gives a starting inventory, while package validity and an application test prove whether a change remains usable.

Decision rule: Before ALTER or DROP, identify object ownership, references, package dependencies, inbound foreign keys, and rollback method. Make additive compatible changes first; destructive changes require a dependency and application rollout plan.

Worked examples and commands

Create a constrained lab table

db2 "CREATE TABLE APP.CUSTOMER_LAB (CUSTOMER_ID INTEGER NOT NULL PRIMARY KEY, EMAIL VARCHAR(320) NOT NULL UNIQUE, STATUS CHAR(1) NOT NULL CHECK (STATUS IN ('A','I')))"

Expected / interpretation: The statement creates a primary key, uniqueness rule, and check constraint; use a disposable schema.

List application tables and types

db2 "SELECT TABNAME, TYPE, STATUS FROM SYSCAT.TABLES WHERE TABSCHEMA = 'APP' ORDER BY TABNAME"

Expected / interpretation: Filter to the exact schema; catalog rows include views and other object types.

Inspect indexes on one table

db2 "SELECT INDNAME, UNIQUERULE, COLNAMES FROM SYSCAT.INDEXES WHERE TABSCHEMA = 'APP' AND TABNAME = 'CUSTOMER_LAB'"

Expected / interpretation: Check actual uniqueness and key order before proposing another index.

Object dependency map: Object definitions and consumers form a dependency chain

A change to a base object can affect each downstream dependent and must be validated across the chain.

Known issues, errors, fixes, and verification

CREATE TABLE fails with SQL0204N.

Likely cause: The referenced schema, table, or other named object does not exist in the connected database.

Fix: Verify database, current schema, object spelling, and catalog visibility; qualify names explicitly.

Verify: Query SYSCAT.SCHEMATA and SYSCAT.TABLES in the same database and authorization context.

DROP or ALTER fails because of a dependency.

Likely cause: A view, foreign key, trigger, package, or routine depends on the target.

Fix: Inventory dependencies and define replacement/rebind/deployment order; avoid CASCADE without a reviewed impact list.

Verify: Requery dependent catalog views and run application prepare/test after change.

An index exists but a query still scans a large table.

Likely cause: The index does not match predicate/order needs, statistics are stale, or optimizer cost favors a scan.

Fix: Capture EXPLAIN and current statistics; design from workload predicates and test in representative data before adding an index.

Verify: Compare explain plans and execution metrics under equivalent bind and parameter conditions.

Hands-on lab: Build an object safely

Objective: Create a small relational object set and document its dependency chain.

  1. Create a disposable schema or use an approved lab schema.
  2. Create parent and child tables with a foreign key and an index.
  3. Query the catalogs to inventory type, keys, constraints, and index names.
  4. Attempt no destructive DDL until the dependency list is complete.

Answer key: The dependency order is parent key, child foreign key, then dependent views/packages; metadata is captured from the same connected database.

Cleanup: Drop child objects before parents, only in the disposable lab schema.

Review question and answer

Question: Why should destructive DDL be preceded by dependency discovery?

Answer: Db2 objects and application packages can rely on the target. Dependency discovery determines safe ordering, rebuild work, and rollback options.
