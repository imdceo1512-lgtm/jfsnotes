Installation, Instance Creation, Profiles, and Service Lifecycle

Identify the active installation, create/manage instances, load the right environment, and start/stop services safely.

Level: Intermediate · Effort: 2.5 hours
Prerequisites: Linux identity and service basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Identify the Db2 copy and instance owner.
  • Load the correct profile and check service state.
  • Explain why instance creation and stopping require change controls.

How it works and when to use it

A Db2 installation can contain one or more copies and instances. The instance owner’s home contains instance configuration and `db2profile`, which sets environment variables and paths. `db2icrt` creates an instance and is an administrative installation action; `db2start`/`db2stop` change service availability. Do not run instance-management commands from an arbitrary shell or on a host whose role is uncertain.

Decision rule: Inventory copy, instance owner, home, service unit, and database list before lifecycle work. Use the required administrative identity and a tested recovery/rollback path for create/update/drop operations.

Worked examples and commands

Load the instance environment and identify its copy

. ~db2inst1/sqllib/db2profile
db2 get instance
db2level
db2ilist

Expected / interpretation: The profile is a shell-specific command for Linux/UNIX. Confirm that the returned instance owner and Db2 path match the intended environment.

Create a lab instance on Linux/UNIX

/opt/ibm/db2/V12.1/instance/db2icrt -u db2fenc1 db2inst1

Expected / interpretation: This requires the documented administrative authority and a prepared instance-owner/fenced-user account. Installation path and options vary; never run against a managed production host as a classroom exercise.

Start the lab instance and confirm the environment

db2start; db2 get instance

Expected / interpretation: Run only on the intended lab host as the instance owner; confirm the returned instance before connecting or creating objects.

Instance lifecycle: Installation copy, instance owner, profile, and service

A lifecycle action is safe only when all four layers refer to the intended target.

Known issues, errors, fixes, and verification

`db2` is not found or reports an unexpected copy.

Likely cause: The shell did not load the intended profile or PATH selects another Db2 installation.

Fix: Source the intended instance `db2profile`, inspect PATH and `db2level`, and use an explicitly qualified utility path for administrative work.

Verify: `db2 get instance`, `db2level`, and the instance home agree.

Instance creation fails on user/group setup.

Likely cause: Owner/fenced IDs, group membership, prerequisites, or installation path do not meet the release requirements.

Fix: Use the installation prerequisite checker and exact Db2 release documentation; correct account setup before rerunning `db2icrt`.

Verify: `db2ilist` lists the new lab instance and `db2start` starts it under the intended owner.

A service starts manually but not through systemd after reboot.

Likely cause: The service unit lacks environment setup or waits for a required filesystem/network mount.

Fix: Correct the service unit and ordering; do not rely on an operator’s interactive shell.

Verify: Restart using the supported service manager and confirm process identity, instance profile, and database availability.

Hands-on lab: Create and start an isolated instance

Objective: Practice lifecycle checks without touching an existing instance.

  1. Use a disposable Linux VM with the required Db2 copy and test accounts.
  2. Record `db2ls`/`db2level`, owner, fenced ID, and intended instance name.
  3. Create the lab instance using the release-specific `db2icrt` syntax.
  4. Load its profile, run `db2start`, inspect state, and stop it cleanly.

Answer key: The procedure proves the correct copy and account setup before creation and verifies the instance through the expected owner/profile after startup.

Cleanup: Remove only the explicitly disposable lab instance using the documented utility; do not run drop commands on production.

Review question and answer

Question: Why must `db2level` be checked after sourcing an instance profile?

Answer: A host can have multiple Db2 copies; the selected PATH may otherwise invoke the wrong installation level.
