Db2 Logging and Recoverability

Read the log lifecycle, recoverability switches, active-log sizing, archive destinations, and the path from committed changes to recoverable data.

Level: Intermediate · Effort: 2 hours
Prerequisites: Database configuration and transaction basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish crash recovery from rollforward recovery.
  • Explain active, archived, mirror, failover, and overflow log paths.
  • Prove whether a database is configured for rollforward recovery.

How it works and when to use it

Db2 writes log records before changed pages are durable. With circular logging, Db2 reuses logs and supports crash recovery, but not rollforward to an older backup. With archive logging, completed logs are retained outside the active path so restore can replay changes. LOGPRIMARY and LOGSECOND bound active-log capacity; LOGFILSIZ sets each log size. Archive destination configuration is a recovery dependency: an image alone cannot replay changes after its backup time. Switching logging mode has activation and offline-backup consequences that must be planned for the current database state.

Decision rule: First decide whether the requirement is crash recovery only or recovery from a backup to a later time. For the latter, prove archive logging, log-chain retention, and retrieval access before relying on it.

Worked examples and commands

Read effective logging settings before changing anything

db2 get db cfg for SAMPLE show detail

Expected / interpretation: Record LOGARCHMETH1/2, LOGPRIMARY, LOGSECOND, LOGFILSIZ, NEWLOGPATH, MIRRORLOGPATH, FAILARCHPATH, and OVERFLOWLOGPATH. SHOW DETAIL distinguishes current and delayed parameter values; it does not prove that the archive target is writable.

Configure an archive destination in an isolated lab

db2 update db cfg for SAMPLE using logarchmeth1 disk:/dbarchive/SAMPLE

Expected / interpretation: This sets a disk archive method. Confirm the path exists with suitable instance-owner access and capacity. When changing from OFF with LOGARCHMETH2 OFF, IBM documents reactivation and offline-backup consequences; follow the exact release procedure.

Inspect current log and archive progress

db2pd -db SAMPLE -logs

Expected / interpretation: Review current log position and archive status alongside effective database configuration; do not remove active log files.

Log lifecycle architecture: Committed changes and recovery log path

An archived image and its log chain are separate inputs to rollforward recovery.

Known issues, errors, fixes, and verification

A backup exists, but the recovery plan cannot roll forward beyond it.

Likely cause: Both archive methods are OFF, so the database uses circular logging and is not rollforward recoverable.

Fix: Plan the archive-logging transition, configure a valid archive target, take the required offline backup, and only then resume the planned workload.

Verify: Read back effective configuration, confirm archival works, and prove restore plus log application in an isolated database.

Transactions pause or logs accumulate while archival is failing.

Likely cause: The archive destination is unavailable, full, incorrectly mounted, or inaccessible to the instance owner.

Fix: Check the exact archive path and diagnostic messages, restore storage/path access, and allow Db2 to retry. Never delete active logs to free space.

Verify: Confirm completed logs archive, active-log headroom recovers, and commit latency returns to baseline.

A log-full incident occurs before expected archive completion.

Likely cause: Active-log demand exceeded configured capacity, a long-running unit of work pins logs, or archive throughput is behind.

Fix: Identify the oldest active transaction and archive backlog; resolve the cause before changing log sizing. Size from measured peak demand and approved capacity limits.

Verify: Compare log utilization and transaction age over the same workload window; validate backup and rollforward continuity.

Hands-on lab: Trace a log from commit to recovery

Objective: Draw and validate the log paths for a recoverable lab database.

  1. Capture database configuration and identify active, archive, mirror, failover, and overflow paths.
  2. Calculate nominal active-log capacity from log counts and file size; document units and assumptions.
  3. Analyze a supplied archive-path failure packet, or simulate a path fault only in a disposable environment.
  4. Restore lab path access, observe successful archival, and record evidence.

Answer key: A non-OFF parameter is not proof by itself. The archive target must work, required logs must remain available, and an isolated restore/rollforward rehearsal must succeed.

Cleanup: Remove only the lab fault, retain original logs, and restore approved configuration.

Review question and answer

Question: Why does online backup require archive logging, and why is archive configuration alone insufficient proof of recovery?

Answer: Online backup requires archive logging. Recovery also requires a complete retained log chain, accessible archive storage, correct target selection, and a successful restore drill.
