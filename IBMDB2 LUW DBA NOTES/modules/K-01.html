Incident Practicum: Log Full, Locks, Storage, and Connectivity

Resolve four competing incident signals with read-only evidence, safe tests, and service-level proof.

Level: Senior DBA practicum · Effort: 3 hours
Prerequisites: A–J; incident response and Db2 fundamentals.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Triage four independent failure patterns.
  • Choose evidence that separates similar symptoms.
  • Write a safe correction and prove business recovery.

How it works and when to use it

Case A has SQL0964C log-full errors and commit stalls; candidate causes include archive failure, pinned long transaction, or insufficient active-log capacity. Case B has SQL0911N lock errors; distinguish deadlock from timeout and identify both applications. Case C has SQL0289N no-page errors; trace table-space growth to path, cap, and filesystem. Case D has SQL30081N connectivity errors; separate alias, DNS, port, TLS, listener, and authentication. Treat all timestamps and target identities as part of the problem.

Decision rule: Rank service impact, capture identity and time window, preserve read-only evidence, then run the smallest test that distinguishes causes. Do not delete logs, force an application, grant broad authority, or expand storage without verifying the constrained layer.

Worked examples and commands

Case A: inspect log configuration and current application state

db2 get db cfg for SAMPLE show detail; db2pd -db SAMPLE -transactions; db2pd -db SAMPLE -logs

Expected / interpretation: Determine active-log headroom, archive path, oldest UOW, and log state before changing settings.

Case B: inspect wait graph and counters

db2pd -db SAMPLE -locks wait; db2pd -db SAMPLE -applications

Expected / interpretation: Map requester/owner and SQL0911N reason code; deadlock and timeout require different evidence.

Case C/D: inspect capacity and connection path

db2 "SELECT TBSP_NAME, TBSP_TOTAL_PAGES, TBSP_USED_PAGES FROM TABLE(MON_GET_TABLESPACE(CAST(NULL AS VARCHAR(128)),-2)) AS T"; df -h /db2data; db2 list node directory

Expected / interpretation: For connectivity, query the client alias then test DNS/port/TLS separately; do not use a DBA SQL query as proof the app can connect.

Incident decision flow: Classify each signal before selecting a correction

Each branch has its own evidence and post-fix proof; a single generic restart is not a diagnosis.

Known issues, errors, fixes, and verification

SQL0964C appears with commit stalls.

Likely cause: Active logs are full due to archive failure, a long UOW pinning log space, or peak log generation exceeding available active-log capacity.

Fix: Inspect archive status, oldest transaction, active-log sizing, and log path capacity; correct the first constraint and preserve active logs.

Verify: Commits resume, log headroom recovers, archive progresses, and representative writes succeed.

SQL0911N appears across several applications.

Likely cause: Deadlock cycle, lock timeout, lock escalation, or a long-running transaction blocks work.

Fix: Use reason code plus lock owner/requester graph; repair transaction order/duration or owner behavior, then retry only a safe idempotent unit.

Verify: The lock wait clears, retry policy succeeds, and lock-timeout/deadlock rates return to baseline.

SQL0289N follows a data load or growth burst.

Likely cause: Tablespace max size, storage path, quota, filesystem blocks, or inodes limit extension.

Fix: Trace logical tablespace to physical path and the exact limiting layer; add approved capacity or correct growth settings.

Verify: Tablespace metrics and host blocks/inodes show headroom and a controlled lab insert succeeds.

Hands-on lab: Four-signal production incident simulation

Objective: Produce a prioritized response plan from a mixed error packet.

  1. Record business impact, target database/member, host, client, and UTC event window.
  2. Classify each error by subsystem and run only the read-only commands relevant to that hypothesis.
  3. Separate confirmed facts from possible causes; name the smallest safe discriminating test.
  4. Propose a correction, rollback point, application proof, and owner communication.

Answer key: The runbook treats four cases independently, avoids destructive actions, and closes each only after application-level service recovery is demonstrated.

Cleanup: Use synthetic logs and lab objects only; no production actions.

Review question and answer

Question: Which error justifies deleting old active log files to recover space?

Answer: None. Preserve active logs and identify archive, transaction, sizing, or filesystem cause through Db2-supported diagnostics.
