Event Monitors and Workload Evidence

Capture historical activity, locking, or statement evidence with an explicit data and overhead budget.

Level: Intermediate · Effort: 1.5 hours
Prerequisites: E-03 and E-04.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Choose an event-monitor type for a specific question.
  • Create, activate, inspect, and deactivate a lab monitor.
  • Control capture scope, output storage, and sensitivity.

How it works and when to use it

Event monitors capture selected events and write them to tables, files, or pipes. Some activate at database activation; others require SET EVENT MONITOR STATE. Activity and statement history can consume monitor heap and storage, and detailed values can expose sensitive SQL or data. Event data must be read with the matching tool/schema and cleaned up only after retention obligations are met.

Decision rule: Start with the smallest event type and duration that answers the question; select output format and storage, activate deliberately, generate synthetic activity, deactivate, then read and remove only lab artifacts.

Worked examples and commands

Create a locking event monitor in a lab database

db2 "CREATE EVENT MONITOR DEADLOCK_LAB FOR LOCKING WRITE TO TABLE"

Expected / interpretation: Use a disposable database; output table names and supported options depend on event groups and release.

Activate and deactivate explicitly

db2 "SET EVENT MONITOR DEADLOCK_LAB STATE 1"; db2 "SET EVENT MONITOR DEADLOCK_LAB STATE 0"

Expected / interpretation: The second statement stops collection after the test. Avoid leaving broad capture active.

Inventory the event-monitor definition

db2 "SELECT EVMONNAME, TARGET_TYPE, OWNER, EVENT_MON_STATE(EVMONNAME) AS ACTIVE FROM SYSCAT.EVENTMONITORS"

Expected / interpretation: Catalog fields can vary by level; inspect the view on the target server before building a cross-release script.

Event capture lifecycle: Define scope, activate, collect, stop, and analyze

Explicit lifecycle control limits overhead and keeps the captured evidence interpretable.

Known issues, errors, fixes, and verification

Event monitor is defined but no data appears.

Likely cause: It has not been activated, no matching event occurred, or output tables/path are unavailable.

Fix: Check event-monitor state, event type, activation behavior, target object, and generated synthetic event.

Verify: Trigger one controlled event and confirm its event record and timestamp.

Monitor capture causes unexpected storage or overhead.

Likely cause: Scope, duration, history details, or captured values were broader than the incident needed.

Fix: Deactivate, preserve required evidence, narrow event types and duration, size output storage, and avoid values unless approved.

Verify: Measure storage and monitor-heap use during a bounded replay.

Event output is unreadable or appears empty in a text editor.

Likely cause: The chosen event-file format is binary or requires the Db2 event reader.

Fix: Use the supported db2evmon/formatting procedure for the selected output, or choose WRITE TO TABLE in a lab.

Verify: Read the output with the matching Db2 utility and reconcile event counts.

Hands-on lab: Capture one controlled deadlock event

Objective: Practice event-monitor lifecycle without collecting broad production history.

  1. Create a lab deadlock monitor with the documented event type and output destination.
  2. Activate it explicitly and run a two-session synthetic lock conflict.
  3. Deactivate the monitor and read the event output with the supported reader.
  4. Record event content, overhead, and exact cleanup steps.

Answer key: The event appears with participants and relevant lock evidence; capture scope and duration are bounded.

Cleanup: Deactivate first, then drop the event monitor and remove only its lab output after retaining approved evidence.

Review question and answer

Question: Why should an activity event monitor not be left collecting indefinitely by default?

Answer: History can consume monitor heap and storage and may capture sensitive statement or value data.
