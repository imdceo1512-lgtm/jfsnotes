Bufferpools, Sort, Package Cache, and Memory Pressure

Use bufferpool, sort, package-cache, and host signals to identify memory pressure before resizing heaps.

Level: Advanced · Effort: 2 hours
Prerequisites: A-03, C-04, E-03.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Interpret bufferpool logical/physical reads by member.
  • Recognize sort spills and package-cache pressure.
  • Change one memory control with effective-value and workload checks.

How it works and when to use it

Database memory is divided among bufferpools, sort memory, package cache, lock list, utilities, and other heaps; host memory pressure can constrain all areas. Logical reads are served through bufferpools; physical reads require storage access. Sort overflows and threshold rejections indicate constrained or spill-prone sorts, but an index may avoid sorting. Package cache eviction and compilation also have workload costs.

Decision rule: Compare member-scoped counters and activity with host memory/swap, data page size, current config, concurrency, and plan. Tune only the constrained area and account for total database/instance memory, not a single heap in isolation.

Worked examples and commands

Measure bufferpool logical and physical reads

db2 "SELECT BP_NAME, MEMBER, POOL_DATA_L_READS, POOL_DATA_P_READS FROM TABLE(MON_GET_BUFFERPOOL(NULL, -2)) AS B"

Expected / interpretation: Use interval deltas by bufferpool/member; a hit ratio can hide direct I/O and mixed workloads.

Inspect database sort settings

db2 get db cfg for SAMPLE show detail | grep -i -E "SORTHEAP|SHEAPTHRES"

Expected / interpretation: Check effective current/delayed values and whether shared or private sort model is configured.

Rank package-cache statements by CPU

db2 "SELECT NUM_EXECUTIONS, TOTAL_CPU_TIME, ROWS_READ FROM TABLE(MON_GET_PKG_CACHE_STMT(NULL, NULL, NULL, -2)) AS T ORDER BY TOTAL_CPU_TIME DESC FETCH FIRST 10 ROWS ONLY"

Expected / interpretation: Package cache counters summarize completed activity and are not a complete memory-pressure diagnosis.

Memory architecture: Memory pressure crosses database and host boundaries

Tune the constrained component only after checking the total host and database memory budget.

Known issues, errors, fixes, and verification

High physical reads are assumed to mean bufferpool is too small.

Likely cause: Sequential scans, cold cache, direct I/O, storage latency, or workload change may dominate.

Fix: Compare logical/physical read rates, access plans, table size, direct reads, and device latency before resizing.

Verify: A controlled workload shows improved response without displacing other memory consumers.

Sort-heavy queries spill to temporary space.

Likely cause: Sort demand and concurrency exceed available per-activity/shared sort memory, or plan requires unnecessary ordering.

Fix: Review plan for avoidable sort, index order, sortheap/sheapthres settings, concurrency, and temp table-space capacity.

Verify: Sort overflow counters and temp I/O decline without increasing host swap or harming concurrent workloads.

Increasing one heap causes host swapping or other regressions.

Likely cause: Total memory allocation exceeded the actual host/container budget or reduced room for other database areas.

Fix: Restore prior value if needed; calculate total memory budget and measure resident/available memory under peak concurrency.

Verify: No sustained swap pressure and all major workload classes retain their latency baseline.

Hands-on lab: Separate bufferpool pressure from sort pressure

Objective: Use workload counters and host memory evidence to avoid resizing the wrong component.

  1. Capture MON_GET_BUFFERPOOL and database-level sort counters at two times.
  2. Record plan operators for a read query and a sort-heavy query.
  3. Correlate those metrics with host available memory and swap.
  4. Propose one reversible lab adjustment and define a no-regression threshold.

Answer key: Diagnosis distinguishes bufferpool physical reads from sort spills and validates total host memory headroom before a change.

Cleanup: Restore lab configuration and remove only synthetic workload.

Review question and answer

Question: Why does a high bufferpool hit ratio not prove the system has no I/O issue?

Answer: The ratio may omit direct I/O, temporary I/O, device latency, and member-specific hot spots.
