Linux CPU, Memory, and Process Diagnosis

Read trends in scheduling, paging, process state, and resource limits without blaming a single high number.

Level: Beginner · Effort: 2 hours
Prerequisites: A-01 and A-02.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Distinguish load from CPU utilization.
  • Identify processes and trends associated with pressure.
  • Correlate operating-system evidence with Db2 activity.

How it works and when to use it

Load average counts runnable and uninterruptible tasks; compare it with CPU count and trends. Memory pressure is about reclaim, page faults, swapping, and cgroup limits—not just free memory. Process state and elapsed time help distinguish CPU work from I/O wait. For Db2, align OS samples with database activities and wait classes; a busy host process can be unrelated to the slow request.

Decision rule: Take repeated samples over the incident interval. If CPU is saturated, identify consumers and queueing; if paging or I/O wait rises, investigate memory/storage; if neither aligns, inspect Db2 locks, agents, and client/network time.

Worked examples and commands

Sample memory and virtual-memory trends

free -h
vmstat 1 5

Expected / interpretation: In vmstat, compare `r`, `b`, `si/so`, `wa`, and swap trends across samples. The first row may report averages since boot; interpret later interval rows.

Find top processes by CPU and memory

ps -eo pid,ppid,user,stat,%cpu,%mem,etime,args --sort=-%cpu | head -20
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,args --sort=-%mem | head -20

Expected / interpretation: Process sorting options are GNU procps-specific. Capture full command identity and elapsed time, then correlate candidate PIDs with Db2 EDU/agent evidence.

Attribute process CPU, memory, and I/O over time

pidstat -urd 1 5

Expected / interpretation: Requires the sysstat package. Compare per-process samples with vmstat and the Db2 application/member evidence.

Known issues, errors, fixes, and verification

High load average is treated as proof that CPUs are saturated.

Likely cause: Tasks can be in uninterruptible I/O wait; load is not CPU percentage.

Fix: Compare runnable and blocked task counts with CPU utilization, iowait, and storage latency over repeated intervals.

Verify: A subsequent sample shows which queue/pressure signal changed after remediation.

The host shows free memory but Db2 reports allocation pressure.

Likely cause: A service cgroup limit, locked memory, fragmentation, or a Db2-specific memory configuration cap is binding.

Fix: Inspect process/cgroup limits and Db2 memory areas; adjust only the proven limit with a measured rollback plan.

Verify: Repeat the same workload and confirm allocation failures and OS pressure both improve.

A high-CPU process is killed as the suspected database cause.

Likely cause: The process may be an unrelated workload or a Db2 worker needed for the current operation.

Fix: Map PID to executable, parent, Db2 EDU/agent, user, and request before intervention; capture evidence and use a controlled stop.

Verify: Check service health, Db2 activity, and workload latency after the approved change.

Hands-on lab: Classify a CPU, memory, or I/O incident

Objective: Choose a discriminating test from a synthetic time-series bundle.

  1. Read five intervals of vmstat and two process listings.
  2. Label runnable, blocked, paging, CPU, and memory signals.
  3. Correlate a candidate process with a Db2 request timeline.
  4. Write one safe next test for each competing hypothesis.

Answer key: Use interval changes and task state to separate CPU queueing, paging, and blocked I/O. Do not kill a process based on one top-process list.

Cleanup: No process changes; retain synthetic samples.

Review question and answer

Question: Which vmstat evidence supports active memory pressure rather than simply low free RAM?

Answer: Sustained swap-in/swap-out, paging/reclaim pressure, and performance impact over time; a single free-memory value is insufficient.
