Run, Monitor, Catalog, and Verify Backups

Follow a backup from command submission through utility completion, history, image inspection, and a separate restore drill.

Level: Intermediate · Effort: 2 hours
Prerequisites: F-03 and Db2 diagnostics basics.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Capture backup identity, scope, timestamp, and outcome.
  • Distinguish header inspection from structural validation.
  • Explain why validation does not replace a restore test.

How it works and when to use it

A backup is an operation with an owner, target, scope, timestamp, output, and resulting artifact set. Multi-session or partitioned images can consist of several objects. The history file helps locate images but can be pruned or stale. `db2ckbkp -h` reads media header information only and does not validate the image; ordinary validation must be run against the complete image set. Validation has limits: a restore and recovery drill is needed to prove the image can serve the intended scenario.

Decision rule: Treat job completion, history entry, header inspection, image validation, and successful isolated restore as separate evidence levels.

Worked examples and commands

Inspect recorded backup history

db2 list history backup all for SAMPLE

Expected / interpretation: Use operation type, start/end time, and image path to reconcile scheduler and storage records. A history row is not an integrity check.

Read media header without validating

db2ckbkp -h /db2backup/IMAGE_FILE

Expected / interpretation: Header-only inspection. IBM explicitly states `-H` does not validate the backup image.

Validate a complete image set

db2ckbkp /db2backup/IMAGE_SEQUENCE_001

Expected / interpretation: Supply every file for a multi-session image, with sequence `.001` first. Validation cannot detect every possible logical or I/O integrity problem.

Backup evidence ladder: Evidence levels from job completion to recovery proof

Each stage answers a stronger question; do not report an earlier stage as proof of a later stage.

Known issues, errors, fixes, and verification

Header inspection is recorded as proof that the backup is valid.

Likely cause: The operator used `-H`, which reads header information only.

Fix: Run the documented validation mode against the complete image set, then schedule an isolated restore/recovery rehearsal.

Verify: Keep separate evidence for header inspection, validation, and restore completion.

Validation fails on a multi-session image.

Likely cause: One or more sequence files are missing or the supplied order is wrong.

Fix: Locate the complete artifact set and pass sequence `.001` first; do not validate just one fragment.

Verify: Repeat validation and reconcile image identity/timestamp with the backup job record.

Automatic restore cannot find a chain although files exist.

Likely cause: History entries were pruned or inventory metadata is inconsistent.

Fix: Use documented incremental-chain tools and manually identify the image sequence; avoid forced history pruning.

Verify: Complete a restore rehearsal and retain required history and all images.

Hands-on lab: Grade a backup evidence packet

Objective: Separate what each artifact proves from what remains unproven.

  1. Review synthetic scheduler output, history rows, image filenames, header output, and validation output.
  2. Label each claim: job completed, artifact found, header read, image validated, or restore proven.
  3. Identify missing sequences and history retention risks.
  4. Write the next safe test required to prove the recovery objective.

Answer key: Job completion/history prove recorded completion. `-H` is header-only. Image validation has documented limits. A restore/recovery rehearsal and application data checks prove usability for the selected scenario.

Cleanup: Use synthetic files; do not change production history or images.

Review question and answer

Question: What can `db2ckbkp -h` prove?

Answer: It displays media header information. It does not validate the backup image.
