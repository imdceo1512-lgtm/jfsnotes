Data Movement: LOAD, IMPORT, EXPORT, and INGEST

Select a transfer utility by volume, logging, constraint behavior, restartability, and recovery obligations.

Level: Intermediate · Effort: 2 hours
Prerequisites: C-01, C-02, and F-01.
Version scope: Db2 LUW 12.1 is the primary reference. Confirm syntax and monitor columns against the installed fix pack; 11.5 compatibility is stated only where checked.
Outcomes · How it works · Examples and commands · Diagram · Known issues and fixes · Lab · Review

Learning outcomes

  • Choose LOAD, IMPORT, EXPORT, or INGEST for a stated need.
  • Recognize LOAD logging, trigger, and constraint behavior.
  • Plan post-load integrity, statistics, and recovery checks.

How it works and when to use it

EXPORT extracts rows through SQL selection. IMPORT inserts through SQL processing and follows insert semantics. LOAD moves pages efficiently, bypasses triggers and ordinary row logging, and delays some checks; it can place tablespaces into pending states depending on options and recoverability configuration. INGEST supports continuous client-driven ingestion but has separate configuration and release prerequisites. Utility choice changes semantics, not only speed.

Decision rule: Use IMPORT for SQL-level insert behavior and moderate controlled loads; use LOAD for bulk movement only after explicitly choosing load mode, copy/recoverability strategy, constraint handling, and post-load checks; choose INGEST for a designed continuous stream.

Worked examples and commands

Export a bounded set

db2 "EXPORT TO /tmp/orders.del OF DEL SELECT ORDER_ID, STATUS FROM APP.ORDERS WHERE ORDER_DATE >= CURRENT DATE - 7 DAYS"

Expected / interpretation: The SELECT defines exactly what leaves the database. Protect exported sensitive data and confirm target path permissions.

Import delimited data in a lab

db2 "IMPORT FROM /tmp/orders.del OF DEL INSERT INTO APP.ORDERS_LAB"

Expected / interpretation: IMPORT uses SQL insertion semantics; define column mapping and validate rejected records.

Bulk load in a disposable table

db2 "LOAD FROM /tmp/orders.del OF DEL INSERT INTO APP.ORDERS_LAB COPY YES TO /db2backup"

Expected / interpretation: COPY YES is a recoverability choice and requires a valid copy destination when applicable; confirm exact prerequisites for the server level.

Utility selection flow: Match movement semantics to the workload

After movement, reconcile rows, resolve pending integrity, gather appropriate statistics, and verify recoverability.

Known issues, errors, fixes, and verification

LOAD completes but triggers did not run.

Likely cause: LOAD operates at page level and bypasses trigger firing.

Fix: If trigger semantics are required, choose IMPORT or a controlled INSERT path; otherwise validate equivalent business rules after LOAD.

Verify: Compare trigger-driven side effects for a synthetic sample and reconcile the load count.

A table space enters backup pending after LOAD.

Likely cause: The load operation or options produced a nonrecoverable state in a recoverable database.

Fix: Follow the reported utility state and take the required table-space or database backup before normal access/recovery expectations resume.

Verify: Check table-space state and confirm the required backup history entry; test an isolated restore path.

Rows are rejected or constraints become pending.

Likely cause: Input values violate types, unique/foreign-key/check constraints, or delayed integrity rules.

Fix: Use a reviewed exception-table/staging design, fix source rows, then run the required SET INTEGRITY workflow.

Verify: Reconcile source, accepted, rejected, and exception counts; query constraints and target rows.

Hands-on lab: Compare transfer paths

Objective: Select and validate a utility for distinct export and bulk-load needs.

  1. Export a limited synthetic result set to a protected lab path.
  2. Load it into a disposable table with an explicit column mapping and reviewed copy option.
  3. Read utility messages and count accepted/rejected rows.
  4. Run integrity and statistics checks required by the selected option.

Answer key: The choice documents utility semantics, required copy/recovery step, rejected row handling, integrity status, and row-count reconciliation.

Cleanup: Remove only lab files and table after counts are recorded; never delete recovery copies.

Review question and answer

Question: Why is LOAD not simply a faster IMPORT?

Answer: LOAD changes logging, trigger, constraint, and table-space recovery behavior. Those semantics and post-load obligations determine whether it is safe.
